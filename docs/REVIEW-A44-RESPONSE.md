# 2. 本轮做了什么

A43 §5 给的顺序是「稳定 variant ID + 多颜色图片绑定 ← 下一轮第一件事」，
`DECISIONS.md` §3.17 写得更硬：**必须先解决稳定 variant ID，再动其他多颜色功能**。
本轮只做这一件，以及在做它的过程中撞见的一个更严重的问题。

## 2.1 变体身份与名字分开 —— **已修复**

### 问题复述

`variant_id_for()` 是一个表达式：`primary_color or sku`。而 `primary_color`
是运营在商品表单里**可以改的一列**。改一次颜色文案，这个表达式同时是三样
东西的主键，三样一起换：

| 消费方 | 改名后的表现 | 看得见吗 |
|---|---|---|
| 图片项变体标签 | 旧标签变 `unknown_tags` | 有诊断 |
| 属性值 `owner_id` | 已确认的颜色属性"消失" | **无声** |
| 导出 SKU 行变体列 | 与上面两者对不齐 | 只有平台会发现 |

A43 把属性分层接到了这个表达式上，于是第二行从"不存在"变成了"存在且无声"。

### 改了什么

| 位置 | 改动 |
|---|---|
| `listings/variant_key.py` | **新增，零依赖纯模块**。归一 / 铸键 / 翻译 / 漂移诊断 |
| `listings/variants.py` | 重写。`variant_id_for` 读列不再算表达式；新增 `variant_label_for` / `assign_variant_key` / `variant_directory` / `resolve_variant_ref` / `drift_report` |
| `models/product.py` | 新增 `variant_key` 列，带 `info={"identity": True}` |
| `migrations/0027_product_variant_key.py` | 新迁移：加列 + 回填 + 索引 + 属性行改写 |
| `services/product_service.py` | 创建与导入两条路都在 `add` 之前分配；`update_product` 拒绝身份列 |
| `listings/image_set_service.py` | 写入侧把标签翻译成 key；`variant_coverage` 增加 `labels` / `drift` |
| `schemas/image_set.py` | 新字段 |
| `frontend/src/api/imageSets.ts` | `VariantCoverage` 类型 |
| `frontend/.../ImageSetTab.tsx` | **第一次把变体覆盖诊断显示出来** |

### 一个需要复核者确认的设计决定：回填取值

0027 的回填是 `COALESCE(NULLIF(BTRIM(primary_color), ''), sku)`，
也就是**迁移前的那个表达式本身**，不是 UUID。

理由：给 UUID 的话，那一句 UPDATE 跑完的瞬间，库里所有图片标签（自由文本，
写的是颜色名）和所有 `(VARIANT, 颜色名)` 上的属性值，全部指向不存在的 key
——一次迁移把这个 bug 在**每一个** SPU 上同时引爆一遍。用旧表达式，升级完成
那一刻所有 id 与升级前逐字节相同，存量数据一条不用动。

代价是 key 看起来像颜色名，会有人想去解析它、或者直接显示它。对策是
`label_of()` 和响应里的 `labels` 字段——**要显示的字符串有一个正确的来源**。
如果复核者认为身份就该是不可解析的，那要连同 0027 的回填、以及存量标签的
一次性重指一起改，不能只改格式。

### 新 SKU 归到哪个变体

`mint_key()` 第一步是「同 SPU 下已有同色的变体 → 复用它的 key」。少了这一步，
红色 S 和红色 M 会拿到两个 key，而"红色缺图"就永远检查不出来。

空颜色**不复用**任何 key：空是"还不知道"，不是一种颜色。把两个未知并成
一个变体等于宣称它们同色。

### 归一做到哪一步

`normalize()` 折叠全角/半角、大小写、随手打的空格、连字符下划线斜杠。
**不做同义词映射**——"藏青"和"navy"是不是同一个颜色，这个模块答不了，
猜错的后果是两个变体被悄悄并成一个，比多出一个变体严重得多。

## 2.2 VARIANT 属性跨 SPU 串档 —— **已修复（本轮发现）**

这条不在 A43 的清单里。是改上面那条时撞见的，比它严重。

`product_attribute_values` 的唯一索引是
`(owner_type, owner_id, field_name) WHERE is_current` —— **里面没有 SPU**。
A43 把 VARIANT 层的 owner_id 直接写成变体 id（取值是颜色名），于是：

> 全库只要有两个 SPU 都有「黑色」，它们就共用同一行属性。
> 给 SPU-SW-001 的黑色确认一次 `primary_color`，SPU-SW-002 的黑色跟着变，
> 没有任何提示。

比"属性不见了"更糟：值还在，只是属于别人。而且它在单 SPU 的测试里永远
复现不出来——要两个 SPU 同色才会出现，而样例数据每个 SPU 一个颜色。

owner_id 现在是 `<len>:<spu>/<variant_id>`，列宽 64 → 160。
长度前缀不是洁癖：SPU 是自由文本，含斜杠不违法，而
`spu="A" + variant="B/C"` 与 `spu="A/B" + variant="C"` 直接拼会得到同一个
字符串。详见 `DECISIONS.md` §3.19。

**存量行只改写能唯一定位到一个 SPU 的那些**（`HAVING COUNT(DISTINCT spu) = 1`）。
剩下的是本来就被共用的那批，归给谁都是猜；原样留着，由
`orphaned_variant_owners()` 的 `legacy_bare` 报出来。

## 2.3 图片标签写入侧翻译 —— **已修复**

变体的身份是 key（分配那一刻的颜色名），界面上给人看的是**当前**颜色名。
改过一次名的 SPU，这两个字符串不同。不翻译的话，人照着界面打出来的标签
全部落进 `unknown_tags`，而同一版里早先绑的旧标签还是好的——表现是
"越是最近绑的图越对不上"，没有人会往三个月前那次改名上想。

`create_set()` 现在先把标签翻译成 key 再去重。顺序有讲究，`test_variant_key.py`
用 AST 钉着：去重的键是 `(media_asset_id, variant_id or "")`，先去重再翻译的话，
同一张图打了「红色」和它的 key 两个标签会被放行，翻译完变成同一项，
而唯一约束在库里——报出来是 500，不是那句能读的 422。

翻不动是 **422 当场拒绝**，不是记 warning。这是人在界面上提交的一次绑定，
提交者就在屏幕前，让他改一个字比让一张图带着谁也不认识的标签进库好。
（识别那条机器路径的取舍相反，见 A43 §BLOCK-03。）

## 2.4 变体覆盖诊断第一次被显示出来

后端从 A42 起就在算 `variant_coverage`，而前端**一个字都没读**。
一个算好了没人看的诊断和没有这个诊断是同一件事，只是前者让人以为自己有。

`ImageSetTab` 现在显示：变体清单（用当前颜色名，不是 key）、哪些已绑定、
全是通用图时的后果说明、两个变体撞名时的告警。**不阻断批准**——今天绝大多数
SPU 的图全是通用图，改成阻断等于让每个多色 SPU 立刻无法批准，那不是修复是停产。

# 4. 本轮新引入的、需要下一位复核者注意的东西

诚实列出，不藏在正文里：

1. **0027 是本项目第一条带数据改写的迁移。** 前 26 条都只动结构。
   它改写 `product_attribute_values.owner_id`，而那张表是属性的事实源。
   `alembic upgrade -> downgrade -> upgrade` 必须在有数据的库上验，
   空库跑通说明不了什么——改写语句在空表上永远是 0 行。

2. **降级会丢东西。** `downgrade()` 把 owner_id 还原成裸形式，
   跨 SPU 串档随之回来。这是功能回退不是数据损坏，但 CI 那条往返
   验的是"能跑"，不是"没损失"，不要把它当作安全性证明。

3. **`variant_key` 的 key 看起来像颜色名。** 它是分配那一刻的颜色名。
   任何直接显示它的地方在第一次改名之后都会显示旧名字。
   界面一律走 `labels[key]` / `variant_label_for()`。
   新写的展示代码如果直接打 key，测试不会红。

4. **翻译层让一类输入从"能提交"变成 422。** 改名之后用旧 key 打标签
   仍然通（第 1 级匹配），但打一个既非 key 又非当前颜色名的字符串
   现在会被拒。A44 之前它会静静进库并在批准时变成 `unknown_tags`。
   这是有意的收紧，但它改变了接口行为，前端没有对应的错误处理测试。

5. **`orphaned_variant_owners()` 只读、无 `--apply`。**
   窗口期里已经被改名甩掉的属性值追不回来——库里只剩一个字符串，
   没有任何地方记着它当初属于哪一件商品。重指归属要靠人判断，
   而本轮拿不到真库，一个能改数据的脚本不该在这种状态下交出去。

6. **`variant_attr_map()` 的签名变了**（多了 `spu`）。全仓只有一个调用点，
   已改，并有 AST 钉着。但它是 public 名字，外部脚本如果调过它会断。

# 5. 放行前必须在 CI 上完成的清单

与 A43 一致，一条不减，**必须绑定同一个 commit SHA**：

```text
PostgreSQL 16 + Redis 7
pytest 0 skip
ruff check app tests
lint-imports
alembic upgrade -> downgrade base -> upgrade   ← 本轮新增 0027（带数据改写，务必在有数据的库上验降级）
npm ci + typecheck + lint + vitest + build
Playwright
前后端 Docker build
```

本轮新增两条**必须在真库跑**的验收，写在这里免得下一轮忘记：

- 0027 回填之后，`variant_key` 与升级前 `primary_color or sku` 的取值逐行相同
- 两个 SPU 各有一个「黑色」变体时，给其中一个确认 `primary_color`，
  另一个的值不变（这是 §2.2 那个洞的直接验收）

任何一个 job 红，都不允许把这一版标记为人工测试基线。
