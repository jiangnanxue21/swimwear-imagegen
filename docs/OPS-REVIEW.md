# 运营视角流程走查与落地

走查方法:以一名运营的一天为主线,从第一次打开系统到平台上架后,
逐环节对照当前代码(不是文档)核实。每个环节给结论:✅ 顺 /
⚠️ 有摩擦 / ❌ 缺环节。

**本文含走查结论与其落地形状两部分。** 走查提出 P1–P5 五条建议,全部已实现;
第二节每条建议下面直接跟着「做成了什么形状、为什么是这个形状、哪些地方刻意没做」。

代码里 20 多处注释以 `OPS-REVIEW P1` / `P3` / `P4` / `P5` 作稳定标识指回本文,
改动那些位置前请先读对应小节。

## 一、逐环节结论

### 0. 第一次打开系统 —— ⚠️ → ✅(P5 已修)

走查时:没填口令时每页报错。`readError` 已让报错明确指向「到系统设置页核对口令」,
列表页也会渲染这句话而不是白屏,能自救。但没有 App 级的「未配置 → 引导到设置页」
检测,新运营要先撞一次错才知道去哪。空表态已有指引
(「先在商品页导入 sample-data/products.csv」)✅。

### 1. 商品进入(新建 / 批量导入)—— ✅

单件:表单必填 + 限长(与后端 field_limits 同源);SPU/SKU 编辑锁定,
不破坏已生成资产的对应。批量:导入页有逐行计划(新建/更新/跳过/报错),
行级错误可见,长度超限在解析期报而不是 flush 撞库。

### 2. 素材上传与角色 —— ✅

上传校验在后端(尺寸/格式);角色(正/背/细节)可改,模型猜的角色带
「角色待复核」黄标,且规则层禁止低把握角色上主图位(§7.3)。
素材隔离在素材库页,要填理由,隔离后已批准图片集自动降级并出
IMAGESET_DOWNGRADED 提示 —— §4.5 第 2 行整条链路是通的。

### 3. AI 生成 —— ✅

任务创建、状态流转、评测、成品图,smoke_test 全程覆盖。付费动作在批量入口有
执行前确认(计划预览 + 「本次触发付费调用 N 次」),幂等回执挡重复付费。

### 4. 属性确认 —— ✅(有一处可加速,见 P3)

逐字段确认;「批量确认」刻意只带待确认项、排除冲突项 —— 冲突必须人眼选,
这个设计是对的。冲突件目前要逐件进详情处理。

### 5. 图片集编排与批准 —— ✅

原生拖拽 + 上下移按钮(键盘可用);第一张图自动设主图(最常见校验失败被预判);
批准后不可原地改,重排走 derive 出新版本回待批准(§4.5 第 3 行)。

### 6. 文案 —— ✅

生成 → 校验(禁词/声明/长度,硬失败与提醒分级)→ 人工可编辑
(编辑落新版本、校验重跑、回待批准,不会把没改的字段一起写掉)→ 批准
(规则版本不一致先强制重校验,§4.5 第 6 行)。「批量生成文案不等于批准」
在批量按钮 Tooltip 里写明,防误解。

### 7. 草稿与手填字段 —— ✅

手填字段从渠道 spec 的 manual_fields 反推生成表单,spec 加字段界面自动跟上;
草稿重建后手填值以服务端为准。过期提示按 §4.5.1 三句话逐条展开
(哪个上游、哪些字段、做什么),旧值新值都摆出来。

### 8. 导出 —— ✅

闸门清单逐项可见 + `canExport` 绑按钮;后端同一份 `export_gate` 二次拦截;
文件名 `{spu}-{渠道}-{时间戳}`;导出历史(次数/时间/操作人)可追溯;
批量导出下载 zip 含上架文件 + 批次清单;页面预览与文件逐格一致有比对器留档(§5.3)。

### 9. 批量运营与异常处理 —— ✅

列表页:四个计数即筛选、五步状态列、阻断/待确认徽标点击直达问题标签页、

单件:REFRESH_DRAFT 一键重生,手填字段不丢。批量:VALIDATE_DRAFT 明文收下
REFRESH_DRAFT 项 —— 模板换版导致 50 件全过期(§4.5 第 5 行)有批量出路,

### 11. 导出之后(上传平台 → 平台审核 → 驳回)—— ❌ 流程在此终止 → ✅(P1 已实现)

## 二、五条建议及其落地

### P1 · 平台侧闭环(驳回回流)

**走查结论。** 流程在「文件已下载」处结束,但运营的一天还有第三幕:上传平台 →
平台审核 → **部分 SKU 被驳回** → 定位驳回的是哪一版图/哪段文案 → 修 → 重导。
走查时:

- 没有平台侧状态(已上传 / 审核中 / 驳回)可记录。平台驳回的商品在工作台里仍显示
  「已完成」绿色 —— 运营只能在系统外拿表格记。
- 没有录入驳回的入口。讽刺的是**数据层早就为它准备好了**:图片集版本化不可变的
  设计理由通篇写着「驳回回流第一件事是定位到具体那一版」,`image_set_rules` 的
  问题码注释也提「进驳回回流的映射」—— 地基打了,楼没盖。
- 任务书通篇没有「驳回」两个字。这是**任务书的缺口**,不是执行的;建议写进下一版
  任务书,排位放在 B1(完整权限)之前 —— 驳回处理慢直接等于上架慢,比权限更接近钱。

**落地形状。**

| 层 | 内容 |
|---|---|
| 枚举 | `PlatformStatus`(NONE/SUBMITTED/LIVE/REJECTED)、`RejectionStatus`(OPEN/RESOLVED) |
| 表 | `platform_rejections`(迁移 `0019`),`listing_drafts` 加平台状态三列 |
| 纯函数 | `workbench/platform.py`:手工转移表、导出版本定位、原因码 → 流程步骤 |
| service | `workbench/platform_service.py`:唯一能写平台状态与驳回台账的地方 |
| API | 4 条(设置状态、记录驳回、列出驳回、标记解决) |
| 前端 | ExportTab 平台面板;`RESOLVE_REJECTION` 进 `NEXT_ACTION_LABEL` / `ACTION_TAB` |

**三个刻意的设计。**

`REJECTED` **不能手工设置**。`manual_targets()` 的返回值里永远没有它 —— 它只能由
「记录驳回」产生。否则平台状态与驳回台账会各说各话:一件「已驳回」的商品没有任何
驳回记录,运营无从知道被驳回的是哪一版、原因是什么。

**有未解决驳回时状态哪儿也去不了。** 先把驳回记录处理掉(标记解决),状态自动退回
SUBMITTED。允许绕过的话,「驳回 2 条未解决」的商品可以顶着「平台已上架」的标签,
比没有平台状态更误导。

**定位把握如实标注三档,不硬凑。**

| `located_by` | 含义 |
|---|---|
| `audit` | 导出留痕带了组件版本(本轮之后的导出),最可信 |
| `current_draft` | 留痕没带版本,但当前草稿指纹与那次导出一致 —— 草稿没重建过 |
| `unlocated` | 老导出 + 草稿已重建。指纹还在,版本对应关系已不可考 |

把 `unlocated` 硬凑成一个版本号比承认「定位不到」更糟:运营会按错的版本去改图。

**驳回件不再顶着绿色「已完成」。** 未解决驳回在 `flow.py` 里产出 **BLOCKING**
问题(`PLATFORM_REJECTED`),于是:自动进异常列表(那一页的条目全部来自 flow 的
`Issue`,不另判一次)、完成度不再让驳回件沉底、唯一下一步变成「处理平台驳回」
并跳到导出页。

### P2 · 完成度计分与任务书对齐

走查发现两处问题,都出在运营每天看的第一个数字上,**当轮即修**:

1. 代码里 STALE 计 60 分、进行中 50 分,而任务书 §3.2 明文过期=0%、进行中=30%。
   后果:一件草稿过期的商品显示 92% —— 按完成度排序它沉底,而它恰恰是导不出去、
   最该被看的那件。已改为 §3.2 口径(0.3 / 0.0),新增测试把计分表逐值钉死
   (数值漂移过一次,所以钉)。
2. 列表页 Tooltip 声称「有阻断时上限锁 90%」—— 代码里**不存在**这个锁。
   注释与代码不一致是最贵的一类缺陷,何况这条写在用户脸上。Tooltip 已改为
   陈述真实公式。

### P3 · 逐件快审(`/workbench-review`)

**走查结论。** 「不做批量批准」是对的 —— 批准必须过人眼。但 50 件全停在
「待批准图片集」时,运营要 50 次「进详情 → 切标签 → 看 → 批准 → 返回」。

**落地形状。先说不做的:仍然没有批量批准。** 批准是人对内容负责的动作,
批量批准等于把审核变成一次点击。这一页压掉的是**导航**,不是审核密度:
原路径 4 步里有 3 步是导航。现在一屏一件,图片集全图与文案全文都在同一屏
(不折叠 —— 折起来的部分等于没审),`J` 下一件 / `K` 上一件 / `A` 批准 /
`Enter` 打开完整详情页。

**队列在批的过程中不自动重排。** 批准一件图片集之后,它的「唯一下一步」会变成
生成文案或批准文案 —— 每批一件就重拉队列的话,手指下的第 3 件会变成另一件商品,
而运营正准备对它按 A。所以队列是**进入时的一次快照**,批过的就地划掉,
要最新队列点「重新载入队列」。

**冲突件不在这一页猜。** 队列来自后端 `next_action=APPROVE_*`;如果打开某件时它的
下一步已经不是批准动作了(别人刚批过、或上游刚变过),批准按钮不亮,横幅写出
当前的下一步与原因,给一个「到详情页处理」的去处,或者按 J 跳过。

契约测试盯住三件事:队列必须来自后端的 `next_action`(前端不自己筛「看起来能批的」,
否则这一页与列表页会给出两份待批准件数);冲突态不许硬批;页面里不出现
`queue.map(` / `Promise.all(` 这类批量批准的形状。

### P4 · 批次文件的作废提示

**走查结论。** 导出后上游又变,单件状态会正确回退(列表可见 STALE)。但运营的
真实疑问是反向的:**「上周导的那个 50 件压缩包,现在还能传平台吗?」**

**这里原来是一条按时间猜的横幅。** 批次页此前的实现是:导出超过 24 小时就提示
「可能含有过期商品」。它两个方向都错 —— 25 小时前导出、什么都没变的批次被冤枉
一次(下次运营就不再读这条横幅了);2 小时前导出、但之后有人改了属性的批次
一声不响,而那份文件正在被传上平台。已删除,契约测试禁止这类痕迹
(`hoursSince` / `BatchStaleBanner` 出现即失败)。

**现在的判定:五态,顺序即语义。**

| 状态 | 含义 | 该怎么办 |
|---|---|---|
| `DRAFT_MISSING` | 草稿已不存在 | 压缩包里它那几行不要再传,确认商品是否已下线 |
| `UPSTREAM_STALE` | 草稿已过期 | **先重新生成草稿**,再重新导出 |
| `SUPERSEDED` | 已被新版取代 | 当前草稿是新的,直接重导一次即可 |
| `UNKNOWN` | 老记录没留指纹 | 无从比对,保守起见重导一次 |
| `FRESH` | 仍然有效 | 可以继续用 |

- **过期优先于被取代**:两者同时成立时先说「重新生成草稿」。反过来说「重导一次
  就行」会让运营点导出、撞上 §4.5.1 的导出闸,再回来看这张表 —— 一次本可避免的错误。
- **UNKNOWN 不计入过期数**:不确定 ≠ 确定失效。但整包也不宣布「可用」。
- **全绿时不显示横幅**:一条「一切正常」的横幅出现三次之后就没人再读横幅了,
  包括真出问题那次。有效条目也不进表(50 行全绿的表没人看)。
- **过期口径一律走 `service.refresh_draft`**:不在批次页凭指纹自己推断一遍,
  否则批次页说「3 件过期」、草稿页说「5 件过期」,正是 §3.4 禁止的两个数字。
  顺带的好处:打开一次批次页也把这些草稿的状态刷到了最新。
- **按 SPU 去重**:导出是 SPU 级动作,同 SPU 的多个 SKU 指向同一份草稿。
- **提前说明「不能整包重新下载」**:`batch_file` 对每一件重跑 `export_gate`,
  过期即 409,而那句错误消息只说「草稿已过期」,不会说「所以你手里那个旧压缩包
  也别传了」。

落点:`batch.file_state()` / `audit_file_states()` / `file_audit_banner()`(纯函数)+
`service.draft_file_facts()` + `batch_service.file_audit()` +
`GET /workbench/batches/{id}/file-audit` + 批次详情抽屉里的横幅与逐件建议表
(每行带「去草稿页」)。

### P5 · 冷启动引导

**走查结论。** 新人第一次打开系统:点哪一页都是一片红,每条错误都写着
「到『系统设置』页核对口令」。信息是对的,但它出现在**每一页的每一个失败请求上**,
而没有一处告诉他:系统是好的,你只差一个口令,填的地方在这儿。

**落地形状。** `ColdStartBanner` 挂在 `AppLayout` 上(不是每页自己加一份 ——
那一定会漏几页,而漏掉的恰好是新人第一次点开的那一页),分三种状态说三句不同的话:

| 状态 | 判据 | 说什么 |
|---|---|---|
| 后端连不上 | `/health` 探测失败 | 检查 `docker compose`;这时填口令没有意义 |
| 口令未配置 | localStorage 里两把口令都为空 | 到设置页填「日常操作口令」;并说明另一把管理口令是干什么的 |
| 口令被拒过 | 任一请求返回 401/403 | 后端在正常运行,但它不认这把口令 |

优先级即上表顺序:后端都没起来时,口令那两句都是噪音。

两处细节:**探活必须用不需要口令的接口**,否则「连不上」与「口令不对」会永远混在
一起 —— `/health` 在后端 `PUBLIC_PREFIXES` 白名单里,且刻意不碰数据库;契约测试解析
`main.py` 的白名单来钉住这条依赖(哪天 `/health` 被移出白名单,探测会变成 401,
横幅就会开始撒谎,而那种缺陷没有任何报错)。**口令好不好只有一份判断**:
`client.ts` 的响应拦截器,成功响应会把「被拒」状态清掉 —— 修好了还赖着不走的警告,
下一次会被连同真问题一起忽略。

在设置页本身不显示横幅(那一页自己会说该填什么),也不在横幅里直接收口令
(设置页是那件事的唯一入口,两个地方都能填就会有人问「我明明填了为什么不生效」)。

## 三、实施 P1 时抓到的一处既有缺陷

`workbench/platform.py` 的模块注释写着「指纹与组件版本的对应关系已进导出审计的
payload」,而写方 `service.record_export` 当时只写了 12 位截断指纹 —— **既没有全量
指纹,也没有组件版本**。

后果不是报错,是**静默降级**:`locate_export` 永远拿不到 `located_by="audit"`,
每一条驳回记录都退到「当前草稿快照」或「版本不可考」。而「草稿重建之后仍能定位到
被驳回的那一版」恰恰是 P1 存在的理由。写方与读方隔着两个文件三层调用,谁都不觉得
自己错了 —— 这与 P2 那条「Tooltip 声称有 90% 上限锁、代码里没有」是同一类缺陷:
**注释与代码不一致,而且不一致的方向是「注释更好听」**。

修法不止是补两个字段,而是把写方和读方放进同一个文件:

| | 位置 |
|---|---|
| 写 | `platform.export_audit_payload()` |
| 读 | `platform.export_entry()` |
| 共用 | `EXPORT_AUDIT_ACTION` 常量、`trim_components()` |

两者相邻定义,由一条**往返用例**钉住:payload 写出去 → 读回来 → `locate_export`
必须判成 `audit`,且 `current_*` 全空(模拟草稿已重建)时依然如此。
顺带确认手填字段(可能含价格)不会被复制进审计表。

`service.record_export` 与 `platform_service._export_audit_entries` 现在都只调这两个
函数,不再各自手拼 / 手解 payload。

## 五、仍然没做的(有意留下)

- **不接平台 API**:平台状态与驳回全是手工录入。接 API 是另一个量级的工作
  (每个平台一套鉴权、一套驳回码),而手工录入已经能把驳回件收回工作台 ——
  这正是 P1 建议里的「最小形态」。
- **驳回原因码不是各平台驳回码的复刻**:它是运营视角的分诊,只回答「该去哪个
  标签页改」;平台原话原样留档在 `platform_note` 里。
- **不做批量批准**(见 P3)。
- **P4 不在 `batch_file` 里改导出闸行为**:过期草稿仍然一律拒绝导出,变化只是
  **在点击之前**把话说清楚。
- **属性冲突件的快审模式**:P3 那套一屏一件可以复用到属性冲突上,尚未做。

## 六、总评

首期范围内的运营闭环是**完整的**,而且多数运营痛点被提前预判了
(自动主图、批量确认排除冲突、过期三句话、异常两层分组、付费确认)。
需要修的不是流程里的环节,而是流程的**终点画早了**:系统把「文件下载」当作
故事结束,运营把「平台上架成功」当作故事结束 —— P1 就是这两个终点之间的距离。
其余各条都是在已经通了的路上铺得更平。

走查过程中抓到的三处缺陷(P2 的 Tooltip、P2 的计分口径、第三节的审计 payload)
是同一类:**注释或界面文案声称的行为比代码实际做的更好听**,而且都不报错。
这类缺陷不会被任何「跑通了吗」式的验证发现,只能靠拿着代码逐环节对文档。
