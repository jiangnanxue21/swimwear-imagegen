# prompts · 提示词注册表与版本

**目录**:`backend/app/prompts/`
**图**:[提示词注册表](../assets/prompt-registry.svg)

## 这张表登记的是什么

仓库里的提示词散在六个模块里。在注册表之前,只有评分那一处能在界面上看到,
其余几处的存在只写在一份 PRD 的表格里 —— 表格不会在新增一处时变红,
也答不出「这个 key 的默认值还解析得出来吗」。

`PROMPT_SURFACES` 是那份盘点的**机器可读版**:每一处答得出 key、层(tier)、
默认值引用、谁在消费、能不能编辑、界面到不到得了。守卫逐条比对。

## 只存元数据,不存正文

正文留在各自领域模块里。`default_ref` 是点分路径(形如
`app.evaluators.vision_schema:DEFAULT_SYSTEM_PROMPT`),`resolve_default()` 惰性解析 ——
本模块**不 import 任何领域模块**,否则 `app.prompts` 会把 evaluators / listings 的
依赖面全部带给每一个 import 它的人(lint 在 services 层,评分键选择在 evaluators 层,
两边都要 import 这里)。

**只依赖标准库与 `app.core`**,守卫用 AST 钉着这一条 —— 破了它,
`grading-stays-pure` 契约迟早跟着破。

`resolve_default()` 解析失败**抛出**而不是吞掉:一个悬空的引用是登记错误,
守卫就该在那里红。

## `editable` 的语义:消费链路会不会读库

**不是「想不想让人改」,是「改了会不会生效」。** `prompt_templates` 表谁都能写,
但只有评分那两份的消费链路走 `get_active_content` 读库;其余几处的正文由代码拼装或
直接引用常量,库里存一版新的,链路**一个字都不会读**。

把那几处标成可编辑,得到的是「保存成功、毫无效果」—— 比「后端通、前端不可达」更糟,
因为它连报错都没有。所以 `PUT /api/prompts/{key}` 按 `editable_keys()` 拦,
`editable=False` 的准确含义写在每一项的 `consumers` 里。

## `ui_reachable=False` 必须写原因

一个「后端支持但前端悄悄看不见」的中间态,不允许无记录地存在。所以这个字段为 False
时,原因必须写进 `consumers`,包括解锁条件是什么。

## 三层模型

统一管理的前提是承认它们形态不同:

| 层 | 形态 | 校验 |
| --- | --- | --- |
| `FREE` | 全文 textarea | 现有 lint + 防注入段存在性 |
| `TEMPLATE` | 措辞可改,必需槽位一个都不能少 | 槽位存在性 |
| `MAPPING` | 键值映射 | 本轮只读 —— 改它等于改修复策略,风险高于改措辞 |

## 版本 = 内容哈希

`prompt_version` 此前有四套口径,其中三套「改了措辞版本号不动」:识别绑 schema 版本、
文案靠人记得改手写常量、出图是函数默认参数。落库的版本号一动不动,
「这一版为什么和上一版不一样」就没法回答,幂等指纹也认不出提示词变过。

现在统一为 `sha256(content)[:12]`:同一份输入恒等,改一个字必变。

`content_version()` 对**非 str 输入直接 TypeError**:序列化的责任在调用方,
而且必须是稳定的。拼装内容里任何不稳定成分(dict 迭代顺序、时间戳、浮点格式化)
都会让同一份提示词每次哈希不同,于是历史记录变成一堆孤儿版本 ——
**那比「版本号不动」更糟,因为它看起来是在正常工作。**

`prompt_templates.version`(自增 int)保留,与它并存:前者回答「这是第几版」,
后者回答「这次调用用的到底是哪段文本」。

## 改提示词是改评分口径

读写都要过 `require_admin`。**能改提示词的人等于能改「什么图算合格」** ——
这比改一个超时值的权重大得多。保存不做内容拦截(已经明确要完全开放全文编辑),
但会把体检结果一并返回,让编辑的人当场看到「你这版没提 JSON」「你删光了硬错误代码」。

署名一律用 `require_admin` 验证过的身份,**不取请求体里的 `updated_by`** ——
否则任何拿到管理口令的人都能把一次改动署名成别人。
