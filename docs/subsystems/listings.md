# listings · 图片集、文案与草稿

**目录**:`backend/app/listings/`

## 图片集不可原地修改

批准之后任何改动都走 `derive()` 生成 `version+1` 的新集。
「平台驳回的是哪一版图」因此永远可查,回滚就是 `approve()` 旧版。

规则在 `image_set_rules.py`(纯函数),service 只负责把库里的行喂进去、把结论写回来。

### 颜色图片规则

- 颜色主图与附图**只能**来自 `variant_id = 该颜色` 的条目;
- SPU 通用图(`variant_id IS NULL`)只能出现在附图位,且必须由运营在编辑器里明确
  标记「通用」,默认不混入;
- **不得回退使用其他颜色的图片 —— 缺图就是缺图**(BLOCKED);
- 必要角度按生成方案的 `angles_json` 验收,**不是只数总张数**。

## 文案按 (channel, site, locale) 独立

独立生成、独立校验、独立重试。多语言一致性靠共享同一份 `ContentPlan.facts`,
**不是**靠一次调用同时出多语言。失败隔离:`en` 通过、`pt-BR` 未通过时只重试后者,
而 `en` 已经可以导出。

校验链:禁词 / 声明 / 长度 → 人工编辑落新版本 → **批准前强制重校验**。
最后这一步是必须的:编辑之后不重校验,等于让人工编辑成为绕过校验的通道。

提示词里的 `{title_max}` 这类运行参数由 `CopyRules` 注入,不写死 ——
「提示词说 120 而校验按 100 判」的事故是这个设计防的。

## 草稿:过期是派生出来的,不是一个状态列

`upstream_versions_json` 存上游各项的版本快照,「是否过期」由逐项与当前版本比较
**派生**,不落 STALE 状态列。这样上游回滚时草稿会自动重新变成有效,
而不需要一个把状态改回去的动作。

范围口径:只检查 `sellable_status=ACTIVE` 的颜色与其 SKU;
PLANNED / PAUSED / DISABLED 不阻塞、不参与映射完整性判定。

过期提示要说清三件事:**哪个上游、哪些字段、该做什么**。

## 导出

一个 SKU 一行、各用途一列,CRLF + utf-8-sig(Excel 双击打开不乱码),批量上限 1000 行。
CSV 注入防护在写出层,不在展示层。
