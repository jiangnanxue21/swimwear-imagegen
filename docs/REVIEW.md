## 0.1 为什么要有这一章

上一版的所有结论都以「当前代码是什么状态」为前提，但没有说明这些前提是怎么来的、是否核对过。
一份决定 25～44 人日投入的方案，如果它的事实基础不可复核，那么后续每一次「是不是已经做完了」的争论都会重新回到记忆和印象。

## 0.3 本次修订的实质性改动

以下五条是新增或修正的内容，也是本次修订的主要价值：

### 1. 补上最大的遗漏：这个仓库没有 CI

全仓无 `.github/`、无 `.gitlab-ci.yml`、无 `Jenkinsfile`。
唯一的门禁是 `make check`，而它只等于 `test-pure + lint` 两项。前端的 `typecheck` / `lint` / `build` 被收在 `make fe-check` 里，需要联网、需要人手动敲。

上一版第 4.1 节 G 列了 11 条门禁、第 10 章列了 12 个勾选框，但**通篇没有说这些门禁由谁执行、什么时候执行、不通过会怎样**。
没有执行者的门禁不是门禁，是备忘录。它会在第一次赶工时被跳过，而且跳过这件事不会留下任何痕迹。

因此本版把「建立最小 CI」提为 P0 的第一项，排在删测试之前。详见 4.1 节 G 与 9.1 节 Phase 0。

### 2. 前端已经有 29 条写好但一行也跑不了的测试

`frontend/tests/unit/` 下有两个文件：

```text
client.test.ts       17 条
workbench.test.ts    12 条
```

而 `frontend/package.json` 的 `devDependencies` 里没有 `vitest`，`scripts` 里没有 `test`，仓库里没有 `vitest.config.*`。

这比「Vitest 未接线」更糟：**目录里躺着 29 条用例，任何人打开这个目录都会认为前端有测试覆盖，但它们从写下那天起一次也没执行过。**
一条从未运行过的测试和一条不存在的测试，可靠性是一样的；区别只在于前者会骗人。

接线任务因此必须包含一条验收：接上 Vitest 后，这 29 条要么全部跑通，要么逐条判定为过时并删除。不允许「接上了但有 5 条 skip」这种中间状态进入人工测试。

### 3. 第 8 章的删除计划算不平自己定的账

上一版设定「减少 25%～30% 的低价值测试函数」，并给出目标结构合计「约 850～1,050」。
但把 8.2～8.7 中每一条明确给了数字的删除项加起来，总量只有约 194～254 条，占 1,390 的 14%～18%。

要达到目标结构中「纯业务逻辑 600～750」，纯测试需要从 1,276 降到 600～750，即删除 526～676 条。
**计划已分配的删除量只覆盖了它自己目标的 40% 左右，缺口约 270～480 条无处着落。**

这不是笔误，是两个数字各自独立提出、从未相乘验证过。本版在 8.1 节重新处理，见下文——处理方式不是硬凑删除清单，而是改掉「以总数为目标」这个错误的 KPI。

### 4. 工期从未合计，且 Phase 2 明显偏乐观

六个阶段的估算分别是 3～5、4～7、6～12、5～8、4～7、3～5 人日，**上一版从未给出合计**。
合计为 **25～44 人日**，单人投入约 5～9 周。这个数字必须写在文档正面，因为它会直接改变「人工测试什么时候能开始」的预期。

其中 Phase 2「Listing 与渠道 API」估 6～12 人日，但它要交付的是：三张全新的表（`ChannelListing` / `PublishAttempt` / `PublishOutbox`，代码中**一张都不存在**）+ 对应迁移 + 字段 Spec + Adapter + 干跑 + 创建 + 更新 + 幂等键 + 外部 ID 落库 + 状态轮询 + 驳回回流 + Simulator + 凭证配置。
下限 6 人日不现实。本版调整为 10～16 人日并说明理由，见 9.1 节。

### 5. 补三处业务上必需但全文未提的内容

- **真实提交后的数据清理预案**：4.1 节 D 要求「少量真实提交」到平台，第 10 章也把「创建成功」列为准入项，但全文没有说这些测试商品事后怎么处理。`PublishOperation` 枚举里已经有 `DELIST`，方案里却一次都没提到它。新增 4.1 节 H。
- **人工测试的退出标准**：上一版把准入标准写得很细（第 10 章 12+ 项），却没有定义人工测试何时算结束、达到什么条件才能进入下一阶段。新增第 11 章。
- **`describe_extractors()` 谎报配置状态**：该函数对包括 `mock` 在内的所有后端一律返回 `configured: True`，与 `providers/registry.py` 中如实调用 `provider.is_configured()` 的做法相反。这直接违反 4.1 节 F「Mock 和真实状态明显区分」的要求，且违反点就在给前端供数的接口上。新增为缺口二的具体条目。

# 1. 执行摘要

重新结合项目目标、A20 代码、运营前端、后端架构和现有测试体系后，最重要的结论是：

> 当前项目已经较完整地覆盖「图片生成」和「Listing 工作台」，但「通过渠道 API 自动上架」仍没有真正成为可运行主链路。

现有实现中：

- AI 图片生成、评分、审核和网站图输出相对成熟；
- 通用 Listing 属性、文案、草稿和文件导出已有完整结构；
- `ChannelAdapter` 已设计 `build_request()`、`submit()`、`poll()` 等正确接口；
- 但 SHEIN 适配器仍是 `TODO_` 骨架；
- 当前没有可用于正式自动刊登的渠道 Adapter；
- 发布域的三张核心表（`ChannelListing` / `PublishAttempt` / `PublishOutbox`）一张都不存在；
- 平台驳回和发布状态主要仍依赖人工录入；
- 真实属性提取器尚未替代 Mock，且状态上报接口谎报为「已配置」；
- 批次并发、回执、费用和导出版本还有若干可靠性缺口；
- **仓库没有任何 CI，全部门禁依赖人手动执行 make 目标**；
- 前端 typecheck、lint、build 从未在流程中跑过，Vitest 未接线，且已存在 29 条无法运行的用例；
- 测试总量 1,390 条，其中大量为源码扫描、AST 和存在性测试，维护成本高而回归保障弱。

因此，人工测试前的工作不能只继续优化页面，也不能只继续补更多静态测试。

人工测试前必须优先完成：

```text
一条真实且可信的端到端主链路
+ 一套不会误导运营的前端
+ 一套真的会自动运行的门禁
```

第三项的措辞相对上一版有意收紧：上一版写的是「可以证明并发、幂等和发布可靠性的自动化门禁」，但**在没有 CI 的前提下，"自动化" 三个字是不成立的**。先让门禁跑起来，再谈它证明了什么。

# 2. 对此前方案的再次反思

## 2.1 之前过度强调「导出文件」，弱化了「API 自动上架」

此前方案大量讨论：

- XLSX/CSV；
- 文件下载；
- 手工确认上传；
- 手工记录平台结果；
- 统一导出中心。

这些能力仍有价值，可作为：

- 渠道 API 不可用时的备选方案；
- 数据核对和审计产物；
- 人工导入的降级路径。

但它们不是最终主链路。

本项目的核心应调整为：

```text
ListingDraft
→ ChannelAdapter.map_fields()
→ ChannelAdapter.validate()
→ ChannelAdapter.build_request()
→ ChannelAdapter.submit()
→ 持久化外部商品 ID
→ ChannelAdapter.poll()
→ 更新平台状态
```

导出文件变为辅助能力，而不是最终交付。

## 2.2 之前把部分生产级复杂度过早列为测试前必做

上一版把以下内容全部提前：

- 完整多人协作；
- 完整统一导出中心；
- 大规模批量恢复；
- 复杂 BI；
- 大量前端高级功能。

这会延迟人工测试，而且其中部分问题只有运营真实使用后才能正确设计。

人工测试前应做到：

- 单件端到端真实可用；
- 5～20 件小批量不会产生明显数据错误和重复付费；
- 核心异常可以恢复；
- API 自动上架有严格干跑和真实测试模式；
- 运营不容易误操作。

不需要在人工测试前做到：

- 500～1000 件无人值守；
- 多团队协作；
- 自动审批；
- 完整组织权限；
- BI 和移动端。

## 2.3 之前把测试数量当成了测试质量——但也不该把「减少数量」当成新目标

A20 当前实测：

```text
测试文件：64
test_* 函数：1,390
纯测试：1,276
集成/DB/HTTP 测试：114
```

数量很多，但其中包含大量：

- 读取源码后搜索字符串；
- 检查函数名称是否存在；
- 检查某文件是否导入某变量；
- 检查 Dockerfile、Makefile 和 `.gitignore` 的文字；
- 使用 AST 推测事务边界；
- 使用 Python 测试前端 TSX 是否包含某段代码；
- 逐条拆分的枚举和标签测试。

这些测试造成三个问题：

1. 重构代码结构时大量无意义失败；
2. 静态测试通过，但真实 TypeScript、数据库或浏览器流程仍可能失败；
3. Agent 为满足测试而保留错误的实现形状。

**但上一版在诊断正确之后，开出了一个方向相反的药方：给总数定一个目标值（850～1,050）。**

这是把一个输出指标当成了输入指标。测试总数是「删掉了多少低价值测试」和「补了多少真实覆盖」两件事相减的结果，它本身不该被瞄准。瞄准它会直接产生两种坏行为：为凑数删掉有用的用例，或者为凑数不敢补该补的集成测试。

本版把目标改写为两条可独立验收的规则，见第 8 章：

```text
规则一：列举出的低价值测试文件，逐个处理完毕（删除 / 迁移 / 参数化合并）
规则二：新增的真实覆盖达到清单要求，一条不少
```

总数是多少，由这两条跑完之后自然得出，不预设。

## 3.2 当前核心缺口

### 缺口一：没有真实自动刊登 Adapter

`backend/app/channels/shein/` 仍是骨架：`spec/common.yaml` 中 33 处字段以 `TODO_` 开头，`__init__.py` 内没有任何实现代码。

这意味着：

- 无真实字段；
- 无真实签名；
- 无真实请求；
- 无类目和枚举；
- 无创建/更新接口；
- 无平台状态轮询；
- 无自动驳回回流。

因此当前不能称为：

```text
自动上架系统
```

只能称为：

```text
具备自动上架架构的图片与 Listing 工作台
```

### 缺口二：真实属性识别未接通，且状态上报会误导前端

两个层面的问题：

**功能层面**：`extractors/registry.py` 的 `_BACKENDS` 只注册了 `mock`，真实多模态模型没有成为生产链路。
（该文件对「未配置时不静默回退 Mock」的处理是正确的，会抛 `ConfigError`，这一点应保留。）

**状态上报层面**：同文件的 `describe_extractors()` 对所有后端一律返回 `configured: True`：

```python
return [{"name": n, "configured": True} for n in sorted(_BACKENDS)]
```

也就是说，**前端问「属性抽取器配好了吗」，后端对着一个 Mock 回答「配好了」。**

这与 4.1 节 F 的要求直接冲突，而且冲突点恰好在给前端供数的那个接口上——运营在界面上看到的是绿的。
修法是现成的：照 `providers/registry.py` 的 `describe_all()` 写，问后端要真实的 `is_configured()`，而不是硬编码。

### 缺口三：平台发布状态不完全可信

目前部分状态依靠运营手工记录，前端还可能把：

- 内容已修改；
- 文件已重导；
- 已重新提交；
- 平台已接受；

混合为「已解决」。

### 缺口四：批次可靠性尚未通过真实并发证明

- BatchItem 原子领取不足；
- 重复 Celery 投递风险；
- 批次重试仍可能同步执行；
- 付费回执和失败迁移需要实库验证；
- 派发可靠性不足；
- Worker 顶层异常可能被吞掉。

### 缺口五：没有 CI，门禁不存在执行者

这是本版新增的缺口，也是优先级最高的一条。

现状：

```text
.github/           不存在
.gitlab-ci.yml     不存在
Jenkinsfile        不存在

make check    =  test-pure + lint          （离线可跑）
make fe-check =  npm ci + typecheck + lint + build + syntax-check  （需联网，需手动）
```

后果不是「某几项没跑」，而是**所有质量约束都退化成了口头约定**。
`Makefile` 自己的注释里写着前端那三条命令「没有任何流程会调用」，且这件事从 A12 就被记录过——一个被发现了八个版本仍然存在的问题，说明它不会靠提醒解决，只会靠自动化解决。

### 缺口六：前端工程门禁未成立

- Vitest 未接线，且已有 29 条用例从未运行（见 0.3 第 2 条）；
- typecheck、lint、build 尚需真实跑通；
- Python 源码扫描仍承担过多前端契约验证；
- Playwright 完全不存在（无依赖、无配置、无用例）。

# 5. 运营视角评审

假设我是每天处理泳衣图片和上架任务的运营，人工测试前最关心的不是后端用了什么框架，而是：

```text
今天要做什么
这件商品卡在哪里
AI 结果是否可信
我应该批准还是退回
商品是否真的提交到平台
失败后下一步是什么
```

## 5.1 运营最需要的完整工作流

### 工作首页

应显示：

- 待审核生成图；
- 待确认属性；
- 待审核文案；
- 待提交平台；
- 平台处理中；
- 被驳回；
- 失败待处理；
- 今日成功上架。

每个数字必须可点击。

### 商品工作台

默认只显示：

| 商品 | 当前阶段 | 当前问题 | 下一步 | 渠道状态 |
|---|---|---|---|---|

避免运营看到：

- 幂等指纹；
- Provider request ID；
- 数据库状态；
- 事务；
- 回执类型。

### 图片审核

运营需要回答：

- 是同一件泳衣吗；
- 肩带、胸垫、腰线是否改变；
- 颜色和印花是否一致；
- 模特是否自然；
- 手指和身体是否畸形；

人工测试前建议完成：

- 原图与生成图并排；
- 全屏；
- 100%、200%、400%；
- 同步平移和缩放；
- 图片集总览；
- 变体切换；
- 明确主图、背面、侧面、细节图。

### 属性审核

模型不能只给一个值，应显示：

| 属性 | 模型结果 | 证据 | 置信度 | 操作 |
|---|---|---|---|---|

运营必须能：

- 确认；
- 修改；
- 标记未知；
- 查看证据图；
- 批量确认低风险字段；
- 单独处理高风险字段。

高风险字段：

- 是否可拆胸垫；
- 是否有钢圈；
- 材质；
- 防晒；
- 速干；
- 件数；
- 内衬；
- 产地。

> 这些字段之所以高风险，是因为它们同时具备两个性质：**看图判断不可靠，且写错会构成商品描述不实**。
> 因此它们的默认值必须是「未知」而不是模型猜测值，且未知必须能阻断发布——这一点在第 10 章列为准入项「未知不猜」。

### 文案审核

针对巴西站：

- pt-BR 文案；
- 中文辅助理解；
- 禁止声明高亮；
- 标题和卖点长度；
- 关键词；
- 事实来源；
- 上一版本差异。

### 自动上架

运营不应只看到「提交成功」。

应分为：

```text
待验证
验证失败
干跑通过
待提交
正在提交
平台已接收
平台审核中
已发布
平台驳回
提交结果未知
```

必须显示：

- 外部商品 ID；
- 最近一次提交时间；
- 操作类型：创建/更新；
- 是否真实提交（真实渠道 / Simulator）；
- 平台返回的安全摘要；
- 下一步。

人工测试前最值得做的运营改造是：

1. 环境和渠道状态明显；
2. 自动上架状态准确；

## 7.4 发布幂等

幂等键至少包含：

```text

shop_id
site
operation
local product ID
draft fingerprint

external listing ID
```

创建和更新不能共用同一个键。
代码中 `PublishOperation` 枚举的注释已经写明了原因——v1 的幂等键不含操作类型，会导致更新被当成重复创建吞掉，或创建被当成更新放过去。实现时保持这一约束。

- 不得立即重新创建；
- 状态进入 `SUBMIT_RESULT_UNKNOWN`；
- 先查询平台或使用幂等键确认；
- 无法确认时进入人工异常队列。

## 7.8 事务边界

建议统一：


- 请求级自动 commit 与 Service commit 混用；
- GET 修改业务状态；
- 一个数据库事务跨越长时间外部调用；

# 11. 人工测试退出标准（本版新增）

上一版定义了何时可以开始人工测试，但没有定义何时算结束。
没有退出标准的测试阶段有两种典型死法：无限延长，或者某天有人说「差不多了」然后上线。

## 11.1 覆盖度要求

- [ ] 至少 30 件真实商品走完全链路（导入 → 生成 → 审核 → 属性 → Listing → 发布 → 平台状态）
- [ ] 至少 3 个批次（每批 5～20 件）
- [ ] 至少 5 件经历过完整的「驳回 → 修复 → 重提交 → 通过」
- [ ] 至少 3 件执行过更新操作
- [ ] 至少 2 次故障演练（Provider 超时、Worker 重启）

## 11.2 质量要求

| 指标 | 退出阈值 | 测量方式 |
|---|---|---|
| 图片一次通过率 | ≥ 60% | 人工审核批准数 / 生成数 |
| 高风险属性准确率 | ≥ 95% | 人工核对，错一个算错 |
| 一般属性准确率 | ≥ 85% | 同上 |
| pt-BR 文案可直接使用率 | ≥ 70% | 运营判定无需改写的比例 |
| 平台提交成功率 | ≥ 90% | 排除平台侧故障 |
| 重复创建事故 | **0** | 平台商品数与本地记录一致 |
| 重复扣费事故 | **0** | `ExternalCall` billable 计数核对 |

后两项是**零容忍**：它们不是质量问题，是正确性问题，出现一次就说明幂等没做对，必须回到 Phase 2 而不是继续测试。

阈值中的百分比是首轮建议值，应在人工测试开始前由运营与业务方确认；确认后写入本文，测试期间不再调整。

## 11.3 遗留问题处置

- [ ] 全部缺陷分类为「阻断上线 / 上线后修 / 不修」
- [ ] 阻断类清零
- [ ] 「上线后修」类有责任人与时间
- [ ] 「不修」类有书面理由

## 11.4 清理与归档

- [ ] 测试期间创建的外部商品全部下架，数量核对一致
- [ ] 测试数据与生产数据隔离确认
- [ ] 真实用量与费用汇总，与预算对比
- [ ] 本文的准入/退出记录归档

# 13. 最终结论

项目最终要求是：

```text
泳衣生成图片
→ 自动形成可上架 Listing
→ 通过 API 自动上架
```

因此，人工测试前最关键的不是再增加更多后台页面，也不是删掉最多的测试函数，而是完成以下闭环：

```text
一套真的会自动运行的门禁
+ 真实图片 Provider
+ 真实属性提取（且如实上报自己是不是真的）
+ 渠道 API Adapter
+ 发布幂等和状态轮询
+ 真实提交后可清理
+ 运营可理解的前端
```

测试体系应从：

```text
大量源码结构测试
```

转向：

```text
少而权威的业务单测
+ PostgreSQL 并发测试
+ Provider/渠道 API 集成测试
+ Vitest
+ Playwright
```

但这个转向有一个前提，上一版没有说出来：**所有这些更真实、更慢、更需要环境的测试，都比源码扫描测试更依赖自动化执行。**
源码扫描测试的唯一优点是零成本、随时能跑；把它们换成集成测试，同时又没有 CI，结果是从「弱保障」直接掉到「无保障」。

所以顺序是确定的：**先有 CI，再谈测试体系升级。**

完成本文 P0 项后，人工测试才能主要发现真正需要人工判断的问题：

- AI 图片质量；
- 泳衣结构一致性；
- 属性准确率；
- 葡语自然度；
- 运营效率；
- 平台真实字段差异。

而不是继续被以下基础问题干扰：

- Mock 冒充真实；
- API 根本没有提交；
- 重复创建商品；
- 重复付费；
- Worker 丢任务；
- 发布状态错误；
- 前端不能构建；
- 测试只验证源码文字；
- 测试写了但从来没跑过。
