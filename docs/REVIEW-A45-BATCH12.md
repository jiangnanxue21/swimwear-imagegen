## 一、这一批修了三条，来源不同

| ID | 一句话 | 来源 |
|:--:|---|---|
| **R-01** | 抽检换选候选图撞终态封闭 → 409 且**审核决策整笔回滚** | 本轮主动排查 |
| **R-02** | 抽检项点「重新生成」→ 同一形状的 409，措辞是状态机内部语言 | 同上 |
| **R-06** | 批量付费动作在 worker 猝死后**自动**重新付费，一路跑到条目重试上限 | 外部指出 |

R-01 / R-02 是同一个错误假设的两处落点：`review_service` 里那两处
`gs.transition` 默认「进来的任务一定还没走完」。A 档抽检恰恰是在任务
**继续往下跑**的前提下开出来的（`NON_BLOCKING_REVIEW_REASONS`），
所以它一定会撞上终态。

## 二、R-01：修法不是给状态机开边

现象是 `COMPLETED -> FORMATTING` 抛 `IllegalTransition`。最省事的改法是给
转移表加一条边——那会把 `state_machine` 顶部「终态不可再转移，防止已完成
任务被后台任务重新拉起」那句话的依据抽掉，而 `reap_stalled`、Outbox 重投、
`_claim()` 全都建立在它上面。

真正要做的只有出图本身。`output_service.build_outputs` 不看任务状态：它按
(商品, 用途) 停用旧图、代数加一，重跑是它设计内的动作。所以终态任务走一条
**只重出图、不动状态**的分支——任务确实已经完成了，换的是选图。

失败**必须抛**，不能像正常路径那样落 FAILED：任务已经是 COMPLETED，
既转不了 FAILED（终态封闭），也没有任何重试入口会捡起它。吞掉的后果是

```
候选图 SELECTED 换成新的     库里说换了
审核项关闭，记 APPROVED      界面上说换成功了
成品图还是旧的那一代          网站上挂的仍然是被推翻的那张
```

三处各说一套，而且没有任何一处会报错。抛出去是整笔回滚——**什么都没发生**
比**三个地方各说一套**好得多。

可重出图的终态**只有 COMPLETED**。另外三个终态的共同点是「这个任务的图
不该出现在网站上」，而重出图恰恰会把它挂上去。这条错了不会报错，只会安静地
把一张被驳回的图发上线，所以单独一个常量加一条断言。

### 顺带修掉一个本批自己造出来的坑

修好之后抽检换图**真的会替换网站上的图**，而 `ReviewDetailPage` 的横幅
原文写着「不会回滚已通过的图」——修复前那条路径是 409，所以这句话
**碰巧**和观察到的行为一致；修好之后它就成了一句错话，而且是最坏的那种：
它让运营以为换一张候选只是记个账。

横幅改成按「有没有真的换过候选」分档：没换 → info，说清两种情况各会发生
什么；换了 → warning，明说会替换线上图并给出退路。**不做常亮警告**——
常亮提示会被训练成噪音，这个仓库在 `unpriced_calls` 那条上已经吃过一次。

## 三、R-06：`executions` 从「事后信号」升级成「闸门」

外部指出的这条成立，而且代码里那段注释直接承认了它：

```python
if route is rules.ReceiptRoute.EXECUTE_AGAIN_BILLED:
    # 上次执行中途死掉(IN_FLIGHT)……只能重跑,**费用会累计**——
    # 台账上这条的 paid_calls > 1 正是要人看见的那个信号
```

问题在于**谁在看**。这条路的发起者是 `reap_batch_leases`（beat 60 秒一拍），
配合 `MAX_ITEM_ATTEMPTS = 3`，一次「外部调用已成功、本地提交前进程死亡」
最多自动付费 **3 次**，全程没有人决定过要不要再花这笔钱。而那个「信号」
出现在台账上的时候，钱已经花完了。

对照生成链路对**同一种不确定性**的处理：

| | 不确定性 | 处理 |
|---|---|---|
| 生成链路 | `SUBMIT_RESULT_UNKNOWN` | 挡住自动重试，`force` 必填人工对账结论，进审计 |
| 批量链路（改前） | 回执 `IN_FLIGHT` | 自动重跑，只写一条 warning |

两个标准，一个系统。这一批把批量侧对齐过来。

### 不需要新列

`batch_action_receipts.executions` 早就存在（迁移 0028），由
`_claim_in_flight` 每次认领 +1，语义正是「这条作用域真的开跑过几次」。
原来它只喂台账，现在同时是闸门。**本批没有迁移。**

### 为什么上限是 2 而不是 1

IN_FLIGHT 有两种成因，标记本身分不出来：

```
崩在调用**之前**   没花钱，重跑免费且正确 —— 绝大多数情况
崩在调用**之后**   花了钱，重跑就是重复计费
```

取 1 等于每一次 pod 驱逐、每一次库抖动都要人工介入，50 件的批次会因为一次
基础设施抖动全部停下——那种代价下这道闸迟早会被关掉。取 2 放过最常见的
那一种，而**同一个点连续崩两次**已经不像偶发，继续付费没有依据。

上限只约束**付费**执行：`FAILED_UNBILLED`、`REUSE_SUCCESS`、
`REUSE_BILLED_FAILURE` 三条不花钱的路一律不受约束，否则一次崩溃会把免费
动作也锁死。两个会计费的入口（IN_FLIGHT 与不可复校的 FAILED_BILLED）
共用 `_billed_again_or_stop`，写成两个 `if` 的话以后只改一处的人不会有提示。

### 闸门必须有出口

停下来之后落 `BILLED_RESULT_UNKNOWN`（`needs_human=True`、
`retryable=False`），于是它拿不到重试按钮，也不会被回收器捡走——这正是
这个码存在的意义。但回执按幂等键索引，而幂等键由动作 + 作用域 + 上游指纹
算出来，**不会自己变**：人去后台核对完「其实没跑成」，没有任何界面能让
这一件重新开始。

没有出口的闸门自己就是一条「核心流程无法继续」。所以同批加了
`tools/resolve_billed_unknown.py`，与 `purge_exports` / `repair_variant_owners`
同一形状：**默认干跑**，`--apply` 必须带 `--note`（人工对账结论，进审计），
且**只解除 IN_FLIGHT**——删掉 SUCCEEDED 会让一个已经成功的动作重新付费执行，
那是这个脚本最容易造成的伤害。

错误提示里直接写了脚本名。断言盯着这一点：提示不指向出口，那道闸对运营
就是个死胡同。

## 八、一个把验证方法本身弄脏的坑（务必记住）

本批的变异验证跑过两遍，**第一遍的结论不可信**。

变异脚本的形状是「写入变异 → 跑测试 → 写回原文」。当这三步发生在同一秒内，
还原后的源文件 **mtime 秒数与大小都和变异版本相同**，而 CPython 的 `.pyc`
校验用的正是 (mtime 秒, size) —— 于是解释器认为缓存仍然有效，
**后续运行的是变异后的字节码**。

表现是：单独跑 `run_pure_tests.py a45_batch12` 20/20 绿，全量跑却多出两条红，
而源码肉眼看完全正确。

修正方法是变异脚本一律带 `PYTHONDONTWRITEBYTECODE=1`，并在开跑前
`find . -name __pycache__ -prune -exec rm -rf {} +`。第二遍在这个条件下重跑，
14 条变异全部变红。

**下一个写变异脚本的人**：这个坑不会报错，它只会让你的门禁悄悄失效，
而失效的方向永远是「看起来更绿」。
