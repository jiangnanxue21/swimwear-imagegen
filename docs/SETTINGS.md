# 后台设置页

Provider 密钥、生成模型、评分模型可以在网页上改,改完不用重启。
本文档是**接入手册**,不是阶段报告。

## 这一块的守卫

| 文件 | 覆盖 |
| --- | --- |
| `test_settings_schema.py` | 字段表与 Settings 对齐、选项与后端注册表对齐、打码、校验、锁与守卫 |
| `test_prompts_and_settings_coverage.py` | 每个可配项都有页面入口;fail-closed 开关必须在页面上并写明理由 |

这一节刻意不写用例条数与总数 —— 写死的数字会在下一次增删用例时立刻过期,
而它过期了不会有任何东西报错。要当前数字请跑 `make test-pure`。
| `test_frontend_contract.py` | +5 | 来源标签、设置页路径、分组→Provider 映射、密钥输入框不回传打码串 |

## 一、这件事本身是在放宽一条规矩

需求第十九章原话是「所有密钥只能来自环境变量」。设置页把它放宽成
「密钥**可以**来自后台,但落库必须加密」。这是一次有代价的取舍,所以先把代价写清楚:

| 放宽前 | 放宽后 |
| --- | --- |
| 密钥只在部署环境里,数据库拿到也没用 | 密钥进了数据库,**必须**加密才不至于比原来更糟 |
| 谁能改配置 = 谁能改部署 | 谁能打开后台谁就能改配置 —— 需要一道新的门 |
| 改配置必然重启,生效时刻明确 | 改完就生效,worker 与后端可能短暂看到不同的配置 |

下面三节分别对应这三行。

## 二、明文永远不进数据库

密钥落库前用 Fernet(AES-128-CBC + HMAC)加密,主密钥按顺序找:

1. `SETTINGS_SECRET_KEY` —— 推荐。多机部署**必须**走这条,否则各节点各自生成、互相解不开。
   填什么都行:本身是合法 Fernet key 就直接用,否则用 scrypt 派生一把。
   运维不需要知道什么是 Fernet key。
2. 密钥目录(`SETTINGS_KEY_DIR`,默认项目根下 `.secrets/`)里的 `.settings.key` ——
   没配时自动生成,文件 0600、目录 0700,并在日志里提醒。
   `docker compose` 里 backend 与 worker 共用一个独立的 `secrets` 卷,所以单机开箱可用。

   > **这个目录不是存储目录。** 早期版本把它写在存储目录里,而存储目录在 local 模式下
   > 被挂成 `/files` 静态服务 —— 主密钥因此可以被直接下载,加密落库这层防护等于零。
   > 现在:密钥目录独立,启动时复查它是否落在存储目录内(落在里面就打 error 日志),
   > 静态挂载另有 `SafeStaticFiles` 拒绝一切点开头的路径段。三道一起,别只靠其中一道。
   > 旧部署首次启动会自动把密钥搬到新位置并删掉原文件,日志里有 `migrated the settings
   > encryption key`;删不掉会再打一条 error 要求手工处理。

拿不到加密能力时(缺 `cryptography`、密钥文件写不进去),
写接口**拒绝保存密钥字段**并说明缺什么。**不降级成明文落库** ——
那会让这次放宽变成纯粹的倒退。

回前端的永远是打码串 `••••••••fKEY`,只留末 4 位。够运营辨认「是不是我填的那把」,
又不足以拼回原值。审计日志只记键名,不记值;日志脱敏本来就命中 `api_key` 这类键名。

主密钥换过之后旧密文解不开 —— 这时返回空串并记一条日志,**不让整个设置页打不开**。
运营看到的是「未配置」,重新填一次即可。

## 三、谁能改:一道运维口令,不是账号体系

MVP 明确排除用户与权限,所以这里没有登录。取而代之的是 `ADMIN_TOKEN`:

- 配了 → 请求头 `X-Admin-Token`,常量时间比较
- 没配 + `APP_ENV` 是 local/dev/development → 放行,本机开发不必为一道口令折腾
- 没配 + 其它环境 → **一律拒绝**,并在错误信息里说清楚要配什么

`test` 刻意**不在**放行名单里:local/dev/development 只可能是某人的开发机,
而「测试环境」在多数团队里是一台真的、连着真 Key、别人也能访问的机器。
少一个字母的差别不该决定要不要口令。

守卫覆盖三个写接口 **以及两个读接口**:`GET /api/settings` 和
`POST /api/providers/{name}/test`。前者会吐出每把密钥的末四位、各家接口地址、
内网下载白名单——凑一起就是一份攻击面清单;后者会拿真 Key 去打厂商接口,
开放它等于把「替你烧额度」和「探测你配了哪几家」一起送出去。
`GET /api/providers`(只列能力与是否已配置,不碰 Key)保持开放。

默认安全而不是默认方便。守卫放在 `app/api/deps.py` 而不是新建 `app/api/auth.py`:
一个 `auth.py` 会把「一道运维口令」看起来变成「账号体系的开端」,
下一个人会往里加用户表。口令校验就三十行,放在 `deps.py` 与其他依赖项一起,
它的份量和它的实现相称。

> 早期这里由一条 `test_out_of_scope_features_are_not_implemented_early`
> 断言守着。那条测试已在测试套件清理时删除 —— 它守的是阶段边界这种项目管理
> 约束,后续正常增加认证、多租户、订单时都会被它挡住。**现在这条约束靠代码
> 评审,没有测试守。** 见 `docs/DECISIONS.md` 第二节。

另一个方向的开关是 `SETTINGS_ENV_LOCK`:打开后,凡是 `.env` 给过值的项在网页上只读,
数据库覆盖也不生效。生产环境建议打开 —— 配置由部署流水线说了算,网页只用来看。

## 四、怎么生效:接在唯一的读配置入口上

全系统读配置只有一个函数:`app/providers/_config.py` 的 `provider_setting()`。
FASHN 的 Key、试穿模型、超时、评分器选择、轮次上限,全都走它。
所以只在它前面挂一层带 TTL 缓存的数据库覆盖层,设置页就对**所有**调用点同时生效,
包括另一个进程里的 Celery worker —— 它自己也会在 TTL 到期后重新读一遍。

```
provider_setting("FASHN_API_KEY")
  → 数据库覆盖(TTL 10 秒缓存,只认声明表里的键)
  → 环境变量 / .env
  → 代码默认值
```

三条刻意的约束:

- **读失败绝不影响主流程。** 数据库连不上就退回环境变量,生成任务照跑。
- **只缓存,不监听。** 没有广播通道,worker 最多晚 TTL 秒看到新值。
  代价是一次任务可能用旧配置,收益是少一个会坏的组件。
- **只有声明表里的键能被覆盖。** 数据库里就算被塞进 `DATABASE_URL` 也不会生效。

顺带把两处原本绕过这个入口的地方接了回来:
`review_service` 的轮次上限、`generation_service` 的默认 Provider。
它们以前直接读 `Settings`,改了配置要重启才生效 —— 那正是这一阶段要消灭的东西。

## 五、能改什么,不能改什么

字段表在 `app/core/settings_schema.py`,是**唯一**的真相来源:
前端不认识任何一个具体配置项,拿到分组、类型、选项就把页面画出来了。
以后加一项只改这一处。

可改:默认 Provider / 路由方式 / 轮次上限;FASHN 的 Key、试穿模型、档位、分辨率、
输出格式与各项超时;fal.ai 与 ComfyUI 的地址与 Key;评分器与视觉模型的地址、模型名、Key;
**抽取器与识别模型的地址、模型名、Key、单次图片上限**(A45-batch14);
内网下载白名单。

「评分模型」与「属性识别」是**两个独立分组**,即便填的是同一个端点也要各填一遍。
不做静默共享的理由在 `docs/DECISIONS.md` §3.24:识别的置信度校准按
(字段 × 模型 × 提示词)分箱存,共享配置意味着换一次评分模型就把识别的
全部校准数据作废 —— 而运营看到的只是「今天开始所有属性都要人工确认了」,
原因在另一个页面的另一个下拉框里。

**不可改**,而且有一条断言钉死:数据库地址、Redis、存储后端、S3 密钥、CORS、
`ADMIN_TOKEN` 与 `SETTINGS_SECRET_KEY` 自身。理由是这些改错就是整站不可用,
或者等于把锁和钥匙放在同一个抽屉里。它们只能走部署。

## 六、测试针对的是「静默失效」

设置页最阴的失败方式不是报错,是**改了没反应**:配置项名字拼错一个字母,
界面照常显示、保存照常成功,只是永远不生效。所以断言都冲着这类问题去:

```
表里的键        必须是 Settings 的真实字段
下拉的选项      必须是 PROVIDER_FACTORIES / TRYON_MODELS / EVALUATOR_FACTORIES 真有的取值
密钥字段        *_API_KEY 必须标 secret;打码串不得残留可用片段;不许把打码串存回去
环境变量锁      必须真的挡住写入,而不只是把界面置灰
生效链路        provider_setting 必须真的读覆盖值(AST 找调用,不是字符串包含)
```

最后一条学的是阶段 7 的教训:`"check_download_url" in source` 那种写法,
把调用删掉只留 import 照样绿。这里一律用 AST 找真实调用节点。

## 七、未完成

- **没有配置变更历史。** 审计日志记了谁在什么时候改了哪些键,但没记改前改后的值
  (记了就等于把明文密钥换个地方存)。非密钥项的前后值其实可以记,留给下一阶段。
- **worker 与后端之间没有强一致。** TTL 期内两边可能用不同配置。
  真要强一致得引入 Redis 广播,当前规模不值得。
- **`ADMIN_TOKEN` 是单一口令,没有轮换机制。** 改口令要重启后端。
- **测试连接用的是已保存的配置。** 想验证一把还没保存的新 Key,得先保存再测。
  做「试填即测」需要把明文 Key 从前端送到一个不落库的端点,风险大于便利,故意没做。
