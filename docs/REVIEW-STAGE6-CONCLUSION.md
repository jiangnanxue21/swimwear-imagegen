**这不是找回原文。** 若后续取得 v3.0,必须逐条差异签认,不能静默覆盖。

### 重述时定死的三个口径

1. **七步不是新定义的。** 它就是 §16 最终产品定义那条管线逐行,
   一行一步,正好七步。自己另编一套七步的话,"完成"又会变成
   一个只存在于实现里的概念。
2. **颜色子态的范围口径与 §6.7 / AC-18 同源**:只有 ACTIVE 颜色拦路。
   另立一套的表现是向导说"这个 SPU 有 2 个颜色缺图"、READY 门禁说
   "可以导出",两处都不报错。
3. **AC-05「不许伪造完成」落在服务端**,不是前端置灰。前端置灰是提示,
   不是门禁 —— 这一条在本仓有先例(§3.43 那一族)。

## 三点五、6-1 的开工方法照做了一遍,结果是空的 —— 这就是 batch26

6-1 的结论里写着 6-2 的开工方法:

> 6-2 开工时**先跑一遍让它们红**,红的清单就是要改的清单。
> 不要反过来先改代码再看哪里红。

照着做了:给 `FlowStep` 加上 `SETUP` 与 `PLAN`,跑 2650 条纯用例。

**后端一条都没红。** 只红了 3 条:两条前端契约测试
(前端的 union 类型与标签表少了新成员)、一条 6-1 自己埋的 `_PLAN_PENDING`。

也就是说 `STEP_ORDER` / `STEP_LABELS` / 完成度 / `evaluate()` 的 `by_step`
四处**都没有穷举守卫**:两个步骤可以进枚举而在后端完全不存在 —— 不算
完成度、不进"唯一下一步"、界面上没有名字,而全仓保持绿色。

`STEP_WEIGHT = 20.0` 那句注释「5 步 × 20 = 100」尤其值得记:它是**算术,
不是断言**。七步之后合计 140,完成度变成一个最大值 140 的数,而它驱动
列表排序与审阅队列。

于是 6-2 之前多插一批(batch26):

- 四条穷举守卫(order / label / weight / `evaluate` 的每步一条);
- `STEP_WEIGHT`(常量)换成 `STEP_WEIGHTS`(逐步表)。**口径没变**,
  换的是它能不能被断言 —— 而 6-2 的口径迁移会集中发生在这张表上;
- 一条 `len(STEP_ORDER) == 5` 的守卫,失败信息里直接写着 6-2 要同批交付的
  四件事。它会在增维那天红,那是它的用处。

反证做过:恢复那两个枚举成员,四条守卫同时变红(此前是零)。

**为什么单独一批而不是塞进 6-2**:它要证明的是"6-2 做错了会红"。
和 6-2 同批的话,守卫与被守的东西一起进来,没人能说清那些守卫是不是
照着结果写的。先落守卫、再增维,顺序本身就是证据。

## 三、6-2 的风险清单(现在就写下来,不等做到那天)


### 3.1 完成度口径会变,而它驱动排序

现在 `STEP_WEIGHT = 20.0`(5 步 × 20 = 100)。加到七步之后,同一件商品的
完成度会从 80% 变成 71%。这不是显示问题:

- 列表页按完成度排序,运营按它找"快好了的那些";
- 审阅队列与批量筛选也读这个数。

口径一变,他昨天记住的那批商品今天不在原来的位置,**而没有任何地方会说
明发生了什么**。6-2 必须同批给出:新权重表、一条说明口径变了的公告文案、
以及一条钉住"权重合计 100"的守卫。

### 3.2 以 `FlowStep` 为键的表会缺项

`FlowStep` 有 113 处引用,其中若干是以它为键的映射(`STEP_LABELS`、
`ACTION_STEP`、异常分类、退回目标)。加两个成员,这些表全部缺项。

好消息是本仓对这类表有穷举契约测试,漏了会红 —— 6-2 开工时**先跑一遍
让它们红**,红的清单就是要改的清单。不要反过来先改代码再看哪里红。

### 3.3 两个新步骤的"完成"定义还没有

- `SETUP`:建了 SPU + 至少一个 ColorVariant + 每个颜色至少一个 SKU?
  还是要求颜色的 `sellable_status` 已经从 PLANNED 动过?
- `PLAN`:选了模特 + 选了生成方案 = 完成?那"方案选了但没跑过"算什么?

这两个问题今天没有答案,而它们决定判定层怎么写。6-2 开工的第一件事是
把这两条写进 PRD 的重述表,不是先写代码再回头补定义。
