### 重述时定死的三个口径

1. **七步不是新定义的。** 它就是 §16 最终产品定义那条管线逐行,
   一行一步,正好七步。自己另编一套七步的话,"完成"又会变成
   一个只存在于实现里的概念。
2. **颜色子态的范围口径与 §6.7 / AC-18 同源**:只有 ACTIVE 颜色拦路。
   另立一套的表现是向导说"这个 SPU 有 2 个颜色缺图"、READY 门禁说
   "可以导出",两处都不报错。
3. **AC-05「不许伪造完成」落在服务端**,不是前端置灰。前端置灰是提示,
   不是门禁 —— 这一条在本仓有先例(§3.43 那一族)。

## 三点五、6-1 的开工方法照做了一遍,结果是空的 —— 这就是 batch26

6-1 的结论里写着 6-2 的开工方法:

> 6-2 开工时**先跑一遍让它们红**,红的清单就是要改的清单。
> 不要反过来先改代码再看哪里红。

照着做了:给 `FlowStep` 加上 `SETUP` 与 `PLAN`,跑 2650 条纯用例。

**后端一条都没红。** 只红了 3 条:两条前端契约测试
(前端的 union 类型与标签表少了新成员)、一条 6-1 自己埋的 `_PLAN_PENDING`。

也就是说 `STEP_ORDER` / `STEP_LABELS` / 完成度 / `evaluate()` 的 `by_step`
四处**都没有穷举守卫**:两个步骤可以进枚举而在后端完全不存在 —— 不算
完成度、不进"唯一下一步"、界面上没有名字,而全仓保持绿色。

`STEP_WEIGHT = 20.0` 那句注释「5 步 × 20 = 100」尤其值得记:它是**算术,
不是断言**。七步之后合计 140,完成度变成一个最大值 140 的数,而它驱动
列表排序与审阅队列。

于是 6-2 之前多插一批(batch26):

- 四条穷举守卫(order / label / weight / `evaluate` 的每步一条);
- `STEP_WEIGHT`(常量)换成 `STEP_WEIGHTS`(逐步表)。**口径没变**,
  换的是它能不能被断言 —— 而 6-2 的口径迁移会集中发生在这张表上;
- 一条 `len(STEP_ORDER) == 5` 的守卫,失败信息里直接写着 6-2 要同批交付的
  四件事。它会在增维那天红,那是它的用处。

反证做过:恢复那两个枚举成员,四条守卫同时变红(此前是零)。

**为什么单独一批而不是塞进 6-2**:它要证明的是"6-2 做错了会红"。
和 6-2 同批的话,守卫与被守的东西一起进来,没人能说清那些守卫是不是
照着结果写的。先落守卫、再增维,顺序本身就是证据。

## 三、6-2 的风险清单(现在就写下来,不等做到那天)


### 3.1 完成度口径会变,而它驱动排序

现在 `STEP_WEIGHT = 20.0`(5 步 × 20 = 100)。加到七步之后,同一件商品的
完成度会从 80% 变成 71%。这不是显示问题:

- 列表页按完成度排序,运营按它找"快好了的那些";
- 审阅队列与批量筛选也读这个数。

口径一变,他昨天记住的那批商品今天不在原来的位置,**而没有任何地方会说
明发生了什么**。6-2 必须同批给出:新权重表、一条说明口径变了的公告文案、
以及一条钉住"权重合计 100"的守卫。

### 3.2 以 `FlowStep` 为键的表会缺项

`FlowStep` 有 113 处引用,其中若干是以它为键的映射(`STEP_LABELS`、
`ACTION_STEP`、异常分类、退回目标)。加两个成员,这些表全部缺项。

好消息是本仓对这类表有穷举契约测试,漏了会红 —— 6-2 开工时**先跑一遍
让它们红**,红的清单就是要改的清单。不要反过来先改代码再看哪里红。

### 3.3 两个新步骤的"完成"定义还没有

- `SETUP`:建了 SPU + 至少一个 ColorVariant + 每个颜色至少一个 SKU?
  还是要求颜色的 `sellable_status` 已经从 PLANNED 动过?
- `PLAN`:选了模特 + 选了生成方案 = 完成?那"方案选了但没跑过"算什么?

这两个问题今天没有答案,而它们决定判定层怎么写。6-2 开工的第一件事是
把这两条写进 PRD 的重述表,不是先写代码再回头补定义。

## 六、AC-05 原来不属于任何一批,batch29 领走了它

§二的分批表里,六条判据的归属是:

```
AC-14   6-2 + 6-3   七步增维 + 颜色子态输出
AC-15   6-3         聚合工作流 API
AC-01   6-4         主流程不离开向导
AC-16   6-4         刷新恢复
AC-17   6-5         上游变化影响提示
AC-05   —           **没有任何一批写着它**
```

这不是排版遗漏,是分批时按"要做什么"切的,而 AC-05 说的是"**不许**做什么"
—— 一条这样的判据很容易在每一批里都被当成别人的事。它在 §一.3 里被强调过
(「落在服务端,不是前端置灰」),然后没有进任何一格。

batch29 领走它,理由是位置对:向导的"下一步"按钮正是那个可能伪造完成的
东西,而它与 AC-01 的 `is_open` 读的必须是同一份判定 —— 那句话就是 AC-05
的最后一行。落点是三条:

```
判定    workbench/wizard.check_action     动作 -> 它属于哪一步 -> 那一步开着吗
接线    api/action_gate.ensure_allowed(_for_spu)  "往前走"的写端点
守卫    没有任何请求体接受 completed / completion / is_done / step_state
```

**接线那一行原来写的是「`api/workbench._ensure_action_allowed` 三个写端点」,
已过期(2026-08-09 评审订正)。** 闸后来搬进了 `api/action_gate.py` 并铺开到
**11 个写端点**,跨 5 个模块:

```
api/attributes.py        2   识别、确认
api/generation_plans.py  2   SPU 默认方案、颜色覆盖
api/image_sets.py        3   建集、编排、批准
api/workbench.py         4   生成文案、批准文案、构建草稿、导出
```

`action_gate.py:19` 有一条 AST 守卫钉住这些函数体里真的出现了那一行调用 ——
所以"三个"这个数字不是保守估计,是**过期的事实**。这一族过期的代价在
§七.2 那条上尤其明显:读者按"只有三个端点"去评估 AC-05 的覆盖面,
会低估已经做到的部分,同时错过真正的缺口(闸只在 HTTP 边界)。

**它带来一次口径收紧**:HTTP 上的「生成文案」从"有任意一个已确认属性"
变成"属性步整体 DONE"。收紧是必要的 —— 两句判据不一样就等于没做。

## 六点五、AC-01 的边界要说准:向导是 product 作用域(2026-08-09 评审补)

§六 那句「唯一把人送出向导的是建档步,而那是 AC-01 允许的『高级异常』」
**只说对了一半**,而漏掉的那一半是结构性的。

AC-01 的重述版(PRD §14.1)把允许的例外限定为三类:**冲突处理、退回、隔离**。
建档步的两种情形要分开算:

| 情形 | 定性 | 依据 |
|---|---|---|
| 存量/导入行**归属没挂** | 站得住的高级异常 | 要人**决定**这个 SKU 属于哪个颜色,按 `spu` 字符串码反查是 §3.39 禁掉的形状 |
| **新建一个 SPU** | **不是**那三类里的任何一类 | 它是第 1 步的常规路径 |

而路由是 `/wizard/:id`,`id` 是 **product(SKU) id**,聚合接口是
`/products/{id}/flow` —— 也就是说**必须先有一行 SKU 才进得来**。
§16 那条管线的第 1 行「创建 SPU / ColorVariant / SKU」因此在向导内
**不可能完成**,不是"被送出去",是根本没有入口。

本轮的收口是**把断掉的那一跳接上**,不是把判据改宽:建档页
(`SpuCreatePage`)建成之后,第一个出口现在是「进入七步向导」,直接落到
`/wizard/{第一个 SKU}?step=MATERIAL`。在此之前那一页只给「去配置生成方案 /
去 SPU 聚合页 / 再建一个」,运营得自己去商品列表里把刚建的 SKU 找出来。

**仍然为真的**:向导本身不能建 SPU。所以 AC-01 的准确状态是
「建档→向导的动线连上了,但建档发生在向导壳之外」——
要做到字面意义上的"七步全程在向导内",得让向导接受一个 SPU 级(或 `new`)
入口并把建档表单收进去。那是一条新口径,本轮不猜,记在这里而不是
悄悄按"高级异常"记成通过。
