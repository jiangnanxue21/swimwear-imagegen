## 二、发现(按严重程度)

### R1(P1)`ColorVariant.skus` 缺 `passive_deletes` —— RESTRICT 在 ORM 路径上被静默绕过

模型注释写着「外键是 RESTRICT,所以数据库会先拦住这件事」,HANDOVER 的
验收清单写着「删颜色被 RESTRICT 拦住」,`test_a45_batch13_spu_db.py::
test_a_color_with_skus_cannot_be_deleted` 断言 `session.delete(variant)` 后
flush 抛 IntegrityError。**三处说的都是同一句假话。**

SQLAlchemy 对"无 delete cascade 的一对多"在删父行时的默认动作是:
**先把子行外键置 NULL,再删父行。** `products.color_variant_id` 本批次恰好
可空 —— 于是两步都成功:"删一个颜色"拿到 200,它下面的 SKU 行悄悄孤儿化,
属性 owner、图片标签、导出变体列同时指空,三者都不报错。这正是这张表
被引入所要消灭的事故,只是换了一个入口进来。全仓 `passive_deletes`
出现次数:**零**。

今天没有删颜色的端点,所以它是**潜伏的致命**而不是现行的:第一个写
删除功能的人会原样踩上去,而那条从未跑过的真库用例会在第一次执行时红 ——
红的不是用例,是它钉的那句验收。

**修**:`passive_deletes="all"`。`True` 都不够 —— 它只是不去**加载**未加载的
子行,已经在 session 里的照样被置 NULL,而"刚建完档马上删颜色"恰好就是
子行全在 session 里的那条路。`"all"` 让 ORM 一个字节不碰,DELETE 直达
RESTRICT。真库用例补了"另一半"断言:IntegrityError 要抛,**并且**回滚后
九行外键原样还在 —— 只断言前一半,"先置 NULL、删父行时撞别的约束"也能绿。

### R2(P1)`update_product` 改受众不同步 `spus.audience` —— 权威被标准操作流分叉

batch13 把 `spus.audience` 定为受众唯一权威(§4.2,模型注释:「受众的权威
从今天起在这一列上」)。而运营改受众的**标准入口**是商品编辑的 PATCH ——
带二次确认弹窗、兄弟行传播、图片集降级、草稿 STALE,一整套。这一套走完:
九份副本全变,权威纹丝不动,且没有任何诊断。今天读取方都在副本上,所以
界面"看起来对";等阶段 1 第二批把读取方切到权威列(或做回填),这次修改被
**静默撤销** —— §3.17 的同一个形状,引信更长。

附带两条同源问题:

1. SPU 管理的行可以把受众清成 NULL。权威列 NOT NULL,于是只有两种结局:
   不同步 —— 权威 WOMEN、九份副本 NULL,分叉;同步 —— flush 撞约束,500。
   两条都不该发生。
2. 兄弟行传播按 `Product.spu == product.spu` 字符串查 —— §4.4(本批次自己
   写的)明令反规范化列禁止作为查询权威。

**修**:三件事,同一个事务里。(a) 入口拒绝 SPU 管理的行清空受众(§4.2:
SPU 层没有"待确认";整个款不做了走 SPU 停用,不是清受众);(b) 副本怎么改,
权威就怎么改 —— `session.get(Spu, product.spu_id)` 后同步 `audience`,
记进审计 cascade(`spu_audience_synced`);(c) 兄弟行 = 字符串命中 ∪ 外键
命中(`or_`)—— 只按字符串违反 §4.4,只按外键漏掉混合期里同款的存量/导入行。
老路径(`spu_id` 为空)一个行为都没变,真库用例里有负向对照钉着。

**刻意不做的**:不给 SPU 层受众修改单独开新端点、不动 §20.5 的二次确认
流程 —— 修的是"权威跟不跟",不是重新设计受众修改;`row_version` 乐观锁
仍留给阶段 1 第二批的并发编辑接口。

### R3(P1)身份禁改名单漏了两列最强的身份

`product_service._is_identity_column()` 自述:「问模型上的
`info={"identity": True}`,**不维护第二张名单**……手写一张名单的话,它会和
模型定义分叉,而分叉的表现是某一天有人加了一列身份、忘了加进名单」。

batch13 往表上加了 `spu_id` / `color_variant_id` —— `identity_of()` 的
**第一级**,改一次三样东西同时换主 —— 恰好没打标记。那段注释警告的失败
形态,在它自己的文件里原样发生。今天 `ProductUpdate` schema 不含这两个
字段,API 打不进来;但那是第二层,设计上的第一道防线已经失效,任何直接
调服务的路径(脚本、将来的批量接口)不设防。

**修**:两列补 `info={"identity": True}`。真库用例验服务层真的拒
(`{"color_variant_id": uuid4()}` → 422)。`spu` / `sku` 两个字符串列
**刻意没动**:它们从 A44 起就只靠 schema 挡,属于存量口径,收进身份名单
是行为变更,超出本轮范围 —— 记在第四节"遗留"里,不悄悄做。

### R4(P2)`identity_shadowed` 没有任何界面渲染 —— 指定的看门狗是瞎的

STATUS 与 §3.23 把这一类指定为回填那颗雷的看门狗(「在那之前由
`drift().identity_shadowed` 盯着」),`imageSets.ts` 的注释说「只有
`label_collisions` 与 `identity_shadowed` 是真问题」。而 `ImageSetTab` 只
渲染 `label_collisions` 和 `key_label_conflicts` —— 看门狗只存在于类型
联合里,类型不渲染任何东西。按本仓库自己的标准:恒报等于不报,
**看不见等于没有**。

**修**:照 `keyLabelConflicts` 的现成横幅样式渲染(列出具体 SKU,给出
下一步:停回填、按 §3.23 三件事一起做),并把它计入横幅的 error 升级条件。
无 node_modules,`tsc` 一次没跑 —— 与 13-2 改 `imageSets.ts` 同一处境、
同一理由;改动逐字镜像既有块,语法风险压到最低,门禁欠账记在第三节。

### R5(P2)`working_name` 为空时,变体目录显示裸 UUID

`ColorVariantCreate.working_name` 在 schema 上默认空串(可选)。只填编码
建档的颜色,`label_for_row()` 三级回落一路掉到身份 —— 目录里那一项是一串
十六进制。13-2 的"目录显示名字不显示 UUID"那条真库用例**每次都填了名字**,
恰好没盖住 schema 自己允许的形状(实测确认:空名 + 空色 → label = uid)。

**修**:`variants._rows` 里显示名回落 `working_name or variant_code`。
"BLK" 不是好名字,但它是运营自己填、印在样品袋上的编码;十六进制谁也
认不出。**编码只用于显示回落,不参与身份判定** —— 身份仍然只有
`identity_of()` 那三级,守卫连回落的顺序一起钉(编码不许压过名字)。

### R6(P2)建档拼 `products.name` 可超列宽,炸出来的还是接不住的那种

`internal_name`(schema 上限 255)+ 空格 + 颜色(≤16)+ 空格 + 尺码(≤8)
最长 **281 > 列宽 255**。internal_name 超过 ~229 个字符时,flush 抛
StringDataRightTruncation —— 那是 **DataError,不是 IntegrityError**,
`create_spu` 里那个 except 接不住,一路裸 500,运营拿不到字段报错。

**修**:`name` 是派生的显示值,不是身份 —— 截断安全,溢出不安全。截到
`limit_for("name")`(与列宽、schema 同一份来源,不写死 255)。守卫两条:
截断的形状(Subscript 上界必须是 `limit_for("name")`),以及截断
**够得着**(最长拼接 > 上限 —— batch13 M9「行数上限永远触发不了」的
同一个教训,别造一条永远不生效的保护)。
