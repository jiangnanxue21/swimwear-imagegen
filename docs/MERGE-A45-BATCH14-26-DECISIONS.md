## 这一批和前几批的分界线

14-23 立过一条规矩:**分界线是缺代码还是缺一个决定**,前者当场写完就能验,
后者写得出来也不该由写的人拍板——替人做完的决定不会有人复核,它会以
"已完成"的身份进下一轮清点。那一批因此只做了"只缺有人写"的那一类。

**本批做的正是被那条规矩挡在外面的三笔。** 授权是显式的("如果有疑问,
按照你的决定来"),所以做法不是绕开那条规矩,是**把它的另一半补上**:

> 决定可以由写的人做,但它必须以**决定**的身份出现,不能以**实现**的身份
> 混进去。四个决定各自单列(见 `DECISIONS.md` §3.41),写清备选方案、
> 选它的理由、以及**选错时会怎样**,并各配一条会在它被悄悄撤回时变红的守卫。

### D1:为什么是外键不是字符串码

14-23 记账时写的是:§4.8 的键要 `spu_id`,所以第一步不是改约束,是先回答
「素材挂 SPU 挂字符串码还是真外键」。

选外键的理由不是"外键更规范",是那个字符串码有一个具体的失效方式:

    改一次 `spu_code`,`products.spu_id` 跟着走(外键),
    `media_assets.spu` 原地断开(字符串码)。

断开之后按 SPU 聚合的素材**静默少掉一批**——不报错、不告警,表现是
「这个款的图怎么少了几张」,而排查的人会先去看上传记录。§4.4 已经为
`products` 付过这笔学费。

`ondelete` 取 **RESTRICT** 而不是 `products.spu_id` 那边的语义:SET NULL
之后那批素材会落进兜底去重键,于是**同一张图在"删 SPU 前"和"删 SPU 后"
的去重结果不一致**。

### D2:按字面落有一个洞

PRD §4.8 行 257 逐字要求 `UNIQUE(spu_id, COALESCE(color_variant_id,''), sha256)`。
但 `spu_id` 可空,而唯一索引里 **`NULL <> NULL`**,一条式落法的后果是:

    所有 spu_id 为空的素材,`(NULL, ..., sha256)` 彼此永不相等,
    于是**它们彻底失去去重**。供应商推十次同一张图,进十行。

那比今天更糟,而且是静默的:约束在,只是不拦任何东西。这类"看起来落了、
实际覆盖零行"的失效与 14-24 记的那次(「0 列都答得出,而退出码是 0」)同型。

所以落两条**互斥且合起来覆盖全表**的局部唯一索引:

    uq_media_assets_spu_colour_sha256   WHERE spu_id IS NOT NULL   §4.8 那个键
    uq_media_assets_product_sha256      WHERE spu_id IS NULL       兜底,即旧键

**这个落法成立的全部前提是两个谓词互补**,守卫钉的正是这一点——不是
"有两条索引"。退化回去最省事的路径不是删掉一条(太显眼),是把某一条的
谓词**改窄**(比如给兜底那条加 `AND legacy_kind IS NULL`):那之后仍然有
两条唯一索引、`spu_id` 仍在、PRD 那个键仍在,而中间裂开一批**两条都不管
的行**,且没有任何地方会报。变异 K3 / K4 演示了这两个方向。

`COALESCE(color_variant_id,'')` 在真类型系统里写成
`COALESCE(color_variant_id::text, '')`——UUID 直接 COALESCE 成空串会报错。
语义与 PRD 一致,差别只在表达式的类型。

第二条**会自净**:老路径从本批起必带 `spu_id`(D4),存量回填完之后它覆盖
零行,那时 `spu_id` 收 NOT NULL、删索引、`variant_key` 退役是同一个动作。
这笔账挂在
`test_the_fallback_dedupe_key_is_owed_a_removal_once_spu_id_goes_not_null`
上,还款日:阶段 5。

### D3:回填走脚本,不在迁移里冻 SQL CASE

迁移不许 import `app.*`(全仓 42 份没有一份破例)。所以在 0045 里回填只剩
一条路:把 `derive_evidence_class` 的四条规则冻成一段 SQL CASE。

**那就是 PRD 风险表 D3 描述的第二个判定点。** 规则今天还在演进,而冻进
迁移的那份不会跟着演进,且停下来之后没有任何地方会报——回填过的行看起来
完全正常。0040 逐条权衡过同一道题并拒绝了,14-23 复述过一次。

本批**不推翻那个结论,而是绕开它**:`app/scripts/backfill_media_assets.py`
早就确立了"大回填走脚本"的先例(迁移跑在一个事务里、几十万行 UPDATE
长时间持锁、脚本可分批可中断可干跑),而脚本**可以** import 派生函数。
于是回填与运行时走同一段代码,"唯一写入点"在回填这条路径上也成立。

守卫扫的是**全部迁移**而不只 0045:退化回去最省事的路径不是"把回填写回来",
是下一个人嫌脚本麻烦,在下一条迁移里补一句 `UPDATE ... SET evidence_class = CASE ...`。

### D4:老建档路径必须解析出 SPU

缝的形状:受众在 SPU 层必填(§4.2),而走老路径建出来的商品 `spu_id` 为空、
`audience` 可空——**必填被绕过了**。

关的方式是**解析**,不是**新建**。这里不调 `create_spu`:那个函数会按尺码
模板展开一整套 SKU,从"建一个商品"里长出十几行商品来;更重要的是它会成为
**第二条建档路径**,而 14-22 刻意不写第二条,理由是两条会各自演进、
然后其中一条先漏掉某个必填项。

**代价写明**:CSV 导入从此要求 SPU 先存在。这是真实的行为变更,不是兼容性
疏漏。放行的代价是每一条走老路径的商品继续绕过受众必填,而那批商品正是
将来 `spu_id` 收 NOT NULL 时挡在路上的那批。爆炸半径核过:1 个路由
(`api/products.py`)+ 1 条真库用例。

受众从 SPU 抄,**不用入参那一份**:信入参的话,调用方可以把商品行的受众
改成和它 SPU 不同的值,而 `category_code_for` 读的是商品行那一份——
于是规则包键按一个受众算、模特与尺码表按另一个受众出。

## 三处"我错了"

这一批有三次判断被工具当场证伪,逐条记下来,因为三次的形状各不相同。

### 一、"守卫太严"——不,它正好

第一版回填脚本写的是 `asset.evidence_class = new`,`test_a45_batch14_7`
的单写入点守卫当场红。第一反应是"守卫太严,调派生函数不该算违规"。

**它不严。** 那条守卫的 docstring 逐字写着禁的是"路由层/**脚本**直写",
而经过一个本地变量之后,在赋值点上**看不出** `new` 是派生来的还是谁手搓的
一段 if。正确的做法是改代码让赋值点本身就是派生调用,不是放宽守卫——
后者与"撤回一个真的违规"在 diff 上长得一模一样。

顺带:不写 `.value`,因为 `EvidenceClass` 是 StrEnum;加上 `.value` 会让
表达式从 `Call` 变成 `Attribute`,守卫又红,而那时正确的做法**仍然**不是改守卫。

### 二、变异 P1 报 GREEN——守卫被同一函数里另一处对的代码喂真

守卫第一版断言 `"ValidationError" in ast.unparse(fn)`。变异 P1 把
`if spu_row is None:` 改成 `if False:`,拒绝路径当场死掉,而函数里
**另一处正确的代码**(`if not spu_code:`)仍然含 `ValidationError`,
断言被喂真。

与 14-22 的 L5 同型(§3.26 那个方向:不是文档喂假断言,是另一段对的代码
喂真)。改成**算**而不是**读**:按 AST 找那条 `if`,断言它的条件真的在比
`spu_row` 与 `None`,且分支里 `raise`。

### 三、`audit_anchors` 报两条锚点断了,都是我造成的

- **14-11 W3 锚点过期**:我把派生块插进了
  `status = MediaStatus.QUARANTINED` 与 `asset = MediaAsset(` 之间,
  而那条变异的锚点靠这两行**相邻**。修法是把派生块移到冲突判定**之前**
  (派生只依赖来源/溯源/角色,与隔离与否无关),而不是改锚点。
  代码里留了一句注释钉住这个位置的理由。
- **14-16 W5 锚点不唯一**:派生调用也按同样两行传溯源,两行式锚点从此
  命中两处。这一条修的是锚点——延长一行(带上构造点收尾的 `)`),
  它验的东西一字未改,仍然是"**构造点**漏写溯源"。

一条什么都没验的变异比没有变异更糟(14-22 的 S3 记过这句),而这两条
在本批之后都会安静地什么都不验。
