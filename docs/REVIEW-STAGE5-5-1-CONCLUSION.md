## 二、评审补齐的五项(已在 5-1 内完成)

1. **事实差异返回字段键而非 UUID。** `color_facts` 的 `fact_versions` 从
   版本集合改成 `{version_id: field_key}` 映射。集合足够回答「是否变化」,
   却无法回答「哪个字段变化」,UI 最终只能显示 UUID。
   这里不引入运行时解析器:解析器会让快照的可解释性依赖**当前**注册表,
   恰好破坏「当时看见了什么」的审计价值。
2. **区分 PLANNED 转正与新建 ACTIVE。** 两者都该过期,但运营动作不同,
   所以必须是两句文案。`inactive` 因此不只是删除/停用的辅助信息。
3. **`ready_problems()` 作为 READY 的唯一合取入口。** `map_problems()` 只管
   SKU 映射,`validate_set()` 只管图片集规则;任何一个单独接到 READY 都会
   静默漏门。
4. **SKU 采集口径写死。** 同一颜色下全部 `products.sku`,不按状态、库存、
   条码、价格再过滤;构建和检查读取同一份采集结果。
5. **两列的 schema version 拆开。** `UPSTREAM_SCHEMA_VERSION` 与
   `IMAGE_MAP_SCHEMA_VERSION`。共用一个版本号意味着任一侧的小改动都会让
   另一侧也不可比,迫使全量草稿两列一起重建。

**A45-batch20 做的是 5-2B,而它没有等 5-2A。** 复核当时把身份前置排在接线
之前,理由是「颜色身份要先统一」。实际开工后发现那个前置**已经不成立**:

5-2A 剩下的是**没有归属外键的存量行**(`products.spu_id IS NULL`)。
batch20 没有兜它们,也没有回填:那条路径如实返回「这个 SPU 在颜色轴上

兜过去(按 `spu` 字符串码反查 SPU 行)是 §3.39 明令禁掉的形状。

## 六、上线演练(NULL 的收口方式)

存量草稿全部在颜色轴不可证明。**不能用 `{}` 回填把未知伪装成空集。**
收口方式是分批重新生成,演练四步:

1. 按 SPU 分批调 `build_draft`,两列随之落库
2. 期间 READY / 导出对未重生成的草稿**禁行** —— 这是预期行为,不是故障
3. 失败的批次重试,重试是幂等的(草稿一个 scope 留一行)
4. 运营公告:说明「颜色维快照」这件事,以及为什么这期间导出会被拦

第 2 步值得提前说:不公告的话,运营看到的是「昨天还能导出的草稿今天不行了」,
而提示写的是一个他没听说过的概念。
