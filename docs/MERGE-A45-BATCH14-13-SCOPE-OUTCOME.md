## 一、为什么是这一条

§11「新增三行」里,另外两行由 14-11 的 §11 批做完了,第三行它**刻意避开**并写明
理由:「PARTIAL_SUCCESS 是 §4.6 的状态机成员,冲突,已避开」。§4.6 那条线是 14-12,
也就是本批的上一批。所以这一行归这条线。

| §11 那一行要的 | 谁给的 | 今天成立吗 |
|---|---|---|
| run = PARTIAL_SUCCESS | `terminal_status_for`(14-12) | ✅ |
| 成功颜色的建议正常入队 | 合并层 + `queue_policy`(§11 批) | ✅ |
| **失败颜色明确列出,可单独重试该颜色作用域** | **本批** | 判定 ✅ / 列出 ❌ |

## 二、开口有多大

`succeeded_count` / `failed_count` 是两个标量。这两种情况在它们眼里**一模一样**:

    3 张图散着失败      每个颜色都还有证据,重不重试都行
    B 色的 3 张全失败    B 色一条证据都没有

而 §6.3 的完成条件要求**每个 ACTIVE 颜色**的必填颜色事实都 CONFIRMED。
第二种情况下那件商品会卡在属性步,而看板上没有任何东西指向 B 色 ——
运营看到的是一件卡住但没有理由的商品,唯一想得到的动作是整批重跑,
**而整批重跑要为已经答上来的 A 色再付一次钱**。

## 三、事后反推不出来,所以这件事欠一列

「这个 run 的输入里,哪几张没有留下证据行」看起来能反推出失败清单。它不能:

`plan_evidence` 在模型只答了目标清单**之外**的字段时返回**空计划**
(§6.3 的编造过滤,14 批落的)。于是一张**调用成功、扣了钱**的图同样
一条证据行都没有 —— 和一张失败的图在库里逐字段相同,而它们一个不该重试、
一个该重试。

所以欠的那一列必须能分辨三件事:这张图**跑没跑**、**成没成**、**属于哪个作用域**。
规格写在 `test_listing_the_failed_scopes_needs_a_column_and_here_is_which_one`,
那一列落库那天它会红。

## 四、为什么不在本批加迁移

本仓有过先例:batch14 在没有真库的机器上加了迁移 0036(「已写、未执行」)。
本批**不照做**,理由不是谨慎,是**并发**:

    三条线同时在这个基线上开工,而迁移链是**单写者资源**
    (`verify_delivery` 盯着「单一 head」)。各自加一条 0037,
    合树时谁都改不动对方的 revision —— 这是三条线里唯一一种
    合树的人无法在本地解决的冲突。

那一列属于 §4.6 那一批(五列 + 一条迁移),由它一次性带走。

## 五、一处放宽与一处收紧,判据都在边界上

**「全军覆没」的判据是「一次都没成功」,不是「有失败」。**写成后者的话,
5 张图里失败 1 张的颜色也会进重试清单,而那个颜色已经有 4 张图的证据 ——
重试它是为一个已经答上来的问题再买一次,而且付的是整个作用域的钱。

**「没有图的颜色」不进结果。**那不是失败,是 §6.2 样品完整度的问题
(`media/sample_completeness.py`),下一步是去拍照。混进来的后果是运营点
「重试这个颜色」,再得到一次空结果,再花一次钱。

这两个边界后来被提成了一个有名字的判定 `scope_lost_everything()` ——
理由见下一节。

## 六、变异第一轮 16/18,两条都值得单独记一笔

**这一节的价值不在最后那个 18/18。**

### F2:一段**没有任何用例够得着**的防御代码

判据原本写在 `outcome_by_scope` 的循环里:

    if outcome.total > 0 and outcome.succeeded == 0:

而颜色是从「确实有图的行」里数出来的,所以循环里的 `total` **恒大于 0**。
删掉那一项不会有任何东西变红 —— 它是一段不可达的防御代码,
而它恰恰是「没有图的颜色不算失败」这条规则的唯一载体。

与 batch14-9 的 S5(指纹里冗余的 `status`)是同一型:**冗余而无法分辨的东西
最容易被顺手清理**。修法与 batch14 的 M9 一致 —— **把判定挪到能穷举的地方**,
不是把断言写得更长:提成 `scope_lost_everything()`,`(total, succeeded)`
的全部小值组合逐组钉死,F2 当场变红。

### S6:变异脚本自己把一次真红误报成「不算数」

S6 把 `getattr` 换成属性访问。它的**正确**失败方式就是一条 AttributeError ——
守卫 `test_a_missing_attribution_column_does_not_explode` 传一个没有那一列的
素材行进去,当场炸。那是一次真红。

而脚本的「导入期就炸了」检测是**在整段输出里找异常名字的子串**,
于是这条真红被判成「不算数」。判据已改成结构性的:套件打印了统计行、
并且点得出是哪条用例红的,就说明它没有炸在导入期。

这条错的方向是安全的(把真红报成不算数,会让脚本退非零、大声喊),
但它和这个仓库栽过五次的那件事是同一句话:**按字符串在输出/源码里找东西,
找到的从来不保证是你以为的那个位置。**

## 七、顺带修掉两条自己人的假绿守卫

上一条那句话当场又应验了一次,这次在**守卫**里。两条守卫都在读
`verify_delivery.WIRED_MODULES`,都用字符串切:

| 守卫 | 怎么切的 | 为什么失效 |
|---|---|---|
| 14-13(本批第一版) | `entry[: entry.index("),")]` | 登记项的注释里有一句 `(归属外键不存在),` —— `),` 提前命中,后面的名字被切没了 |
| **14-12(已交付)** | `wired[...][:200]` | 一个**定长窗口**。本批往那个登记项里加了 `outcome_by_scope` 和一段注释,窗口就切在半路上 |

14-12 那条更值得看:它的正向断言碰巧还在窗口内,而**反向**断言
(「`idempotency_key` 不许被登记」)被切出来的残段喂成了**平凡真**。
也就是说,本批往登记项里加一行的那一刻,那条守卫悄悄不设防了,
**而它照样显示 PASS**。

两条都改成用 AST 读 `WIRED_MODULES`,并且**验过它们真的咬得住**:
把 `idempotency_key` 临时登记进去,两条当场变红。

## 八、接线接的是形状,不是行为

`run_extraction` 的循环两条分支各记一条逐图成绩,跑完交给 `outcome_by_scope`。
**今天它一定给出空清单** —— `scope_of` 读的是阶段 2 的归属外键
`color_variant_id`,那一列不存在,于是每张图都落在共享作用域里。

那为什么现在接:接的是形状。那一列落库那天,不接线的表现是「判定写好了没人调」,
而最省事的补法是就近抓一个 `variant_hint` 来分组 —— 那是让模型猜出来的值
决定**重试范围**,而重试范围决定下一次付多少钱。14-9、14-10 两次拒绝接线是
同一条理由,这里是第三次,而这次它成了变异 S5。

`scope_of` 用 `getattr` 而不是属性访问,与 `evidence_rules.asset_is_extraction_input`
同一处理:属性访问会在列落库**前**当场炸,写死 `None` 会在列落库**后**继续瞎。
